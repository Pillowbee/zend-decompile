# Zend Decompiler v23 — отчёт по инженерной итерации

**Статус**: экспериментальный offline-декомпилятор. Исходные закодированные файлы **не исполнялись**; PHP 5.2.17 применён лишь для `-n -l` собственных тестовых исходников и синтаксиса кандидатов. Ни semantic equivalence, ни production readiness не доказаны.

## A. Нативный источник опкодов и эмпирические ключи

**Проверено**: локальный `php52_linter -n -v` сообщает PHP 5.2.17, Zend Engine 2.2.0. Пробный компилятор `zend_work/probe_with_cv.so` (историческое исследовательское расширение, ABI задан вручную) действительно выдаёт `op_array` на собственных PHP программах в `-n -l`. Дамп нормализован: номера, строки, extended_value, имена CV без указателей ASLR.

**Источник**: `corpus/own_sources/01_calls.php`—`05_inheritance.php`. Дампы: `corpus/compile_only_dumps/*.log`; нормализованные версии `*.normalized.json`; SHA256 исходников в `corpus/manifest.json`.

**Не найдено в среде**: `zend_compile.h`, `zend_vm_def.h` и `zend_vm_opcodes.h`, однозначно соответствующие именно скомпилированному установленному бинарнику PHP 5.2.17. VLD не найден. Поэтому независимая проверка всех ключей Encoder не выполнена.

**Подтверждения и гипотезы**: в `02_foreach.php` собственный нативный дамп содержит `77`, `78`, затем `49`; в наследовании `05_inheritance.php` opcode 140 не встретился. Это наблюдения *нативного компилятора*, но они **не устанавливают**, чему соответствует зашифрованный ключ `1:199`. `opcode_hypotheses_v23.json` описывает три нерешённых случая: `140`, `1:199`, `49`. Таблица v20 и v21 evidence неизменны: **0 confirmed / 305 inferred / 9 unknown** (314 записей evidence, 313 маппингов).

Таблица подключается флагом `--map`; рядом с ней может располагаться `<map-file>.meta.json` с хешами mapping/evidence, вариантом сериализации и источником. Несовпадение SHA256 приводит к отказу.

## B. Round-trip и корпус

Команда воспроизводимого compiler oracle (только собственные исходники):

```bash
LD_LIBRARY_PATH=/mnt/data/php52_libs \
  ./php52_linter -n \
  -d zend_extension=/mnt/data/zend_work/probe_with_cv.so \
  -l corpus/own_sources/02_foreach.php
```

Проверена повторная компиляция всех пяти файлов в `test_compiler_oracle_v23.py`: **5/5 файлов**, **5 именованных op_array** (включая методы), **93 нативные инструкции**. Дамп соответствует сохранённым нормализованным результатам. Количество программ, подходящих для восстановления тем же декодером: **0**; успешность по файлам/функциям записана `null`, а не нулём. `corpus/metrics.json`: `round_trip.status = not_run`.

Причина отсутствия адаптера: `zend_serial_parser.parse_binary()` сначала проверяет length-prefixed заголовок `SSG Team`, затем парсит `Reader.node()` с serialized operand types (1/2/4/8/16), trailer с CV и зашифрованный ключ `(index % 8, raw_opcode)`; нативный probe выводит внутренние `zend_op` уже после компиляции и не предоставляет исходного SSG-потока или эквивалентного байтового zval-кодирования. Простая перестановка полей не даст доказуемого преобразования.

Технически более подходящая альтернатива — адаптер от **расширенного native op_array oracle с точными операндами и структурами типов** к новому IR, минуя Encoder-сериализацию. Для полноценной проверки необходимы соответствующие заголовки точной ABI и надёжная нормализация временных ячеек/контрольного потока. Дамп в v23 — только начальная часть этого шага.

## D. Реальные правила декодера и диагностика

`Decoder.run()` теперь увеличивает `fired_rules[kind]` после завершения реальной ветки обработки (не при одном распознавании имени). `build_group()` и резервный `state_emit()` собирают счётчики по полностью декодированным группам. `zend_engine.restore_result()` считает `rule_usage` и `supported_*` только по успешным обработчикам. Например, у `import(1).php` `BOOL_NOT = 1`, `supported_unary_bool_not = true`, `supported_simple_at_function_call = false`; у `user.php` оба флага false. **Режим `restore_v20_compat()` сохраняет исходный v20 audit для golden-тестов**, включая прежние константы.

`Decoder.current_index` позволяет записать точную инструкцию в сообщении об ошибке. В примерах: `links_fun(1).php`: `<main>/B012/opcode #12: SEND without call`; `fun_all.php`: `out_link/B016/opcode #16: Unresolved temporary (2,0,0)`. Контекст включает окно ±2, opcode key и `confidence`. `group_diagnostics` и новый `group_coverage` batch-отчёта имеют доли нумерически распознанных и **подтверждённых независимыми источниками** инструкций; последние пока равны 0.

## E. Недоверенный ввод и инженерия

- `zend_parser_isolated.parse_isolated`: **Linux-only** subprocess с `RLIMIT_AS=512 MiB`, `RLIMIT_CPU=3 s` (hard 4 s), wall-clock timeout 5 s, ограничение входа `MAX_BINARY=64 MiB`. Используется **опционально**, CLI `--isolate-parser`. Это предварительная проверка **парсера**, а не изоляция всего восстановителя.
- Первоначальный лимит 256 MiB отбрасывал нормальный `fun_all.php` с `MemoryError`. Это выявлено и исправлено: 512 MiB пропускают все контрольные разобранные потоки. Итоговый batch выполнен с `--isolate-parser`.
- `zend_fuzz_v23.py`: фиксированный seed 20261021, 185 случаев (5 краевых + 180 мутаций) → 19 распознано, 166 отклонено, 0 неожиданных исключений; отдельные изолированные проверки завершились корректно. Программа сохраняет неожиданные падения как `.bin` и `.json` в `tests/fuzz_regressions`; четыре известные битые последовательности сохранены заранее.
- Имена функций в активных путях декодируются строго как ASCII, что соответствует `sym()` (идентификаторы вне этой поддержки **отклоняются**); исходные PHP-строки по-прежнему обрабатываются как байты/CP1251. `mapping_file.read_text(encoding='utf-8')`; удалён повторный внутренний импорт `sym`.
- `zend_crossblock_v12.py` и `zend_crossblock_v17.py` **не являются одинаковыми файлами**: различается импорт Decoder (v11 против v17); первый нужен старому preview-модулю. Не удалён.
- Никакие тесты `user_tests/harness.php`, `user_tests/original.php` не запускаются в `tests/` или CI; `test_schema_and_packaging_v23.py` проверяет конфигурацию workflow. PHP для закодированных исходников не запускался.
- Wheel 23.0.0 собран. `networkx` требуется при установке; проверка вне каталога исходников с предоставленной зависимостью создала кандидат `basket.php`, PHP 5.2 синтаксис прошёл. `zend-decompiler validate` из wheel теперь завершает работу с кодом 2 и сообщает, что нужны исходные fixtures, вместо ложного «успеха 0 тестов». Автоматический GitHub Actions запуск не подтверждался; локально воспроизведена команда workflow.

## C. Ядро и риски

Новых handlers `FE_RESET`, `FE_FETCH`, `list()`, `isset/empty`, `try/catch`, межблочного dataflow, настоящего CFG structurer **нет**. Исследование и план по файлам — `IR_MIGRATION_V23.md`. Вмешательство в восстановление семантики отложено до валидированного round-trip на собственном корпусе. Нельзя засчитывать прирост только из-за прохождения `php -n -l`.

## Проверка — воспроизводимые команды

```bash
cd zend_decompiler_v23
python -m unittest discover -s tests -v
python zend_cli.py validate
python zend_fuzz_v23.py --source sample_inputs/basket.php --dictionary zend_verified_dictionary.bin --mutations 180 --isolate-every 30 --report corpus/fuzz_v23.json
```

## Недостающие данные и допущения

1. Проверенные *именно для текущей сборки* `zend_compile.h`, `zend_vm_def.h`, `zend_vm_opcodes.h`, информация о патчах компилятора, либо сборка PHP 5.2.17 из известных исходников и заголовков.
2. Дамп всех полей опкодов native PHP 5.2 (можно расширить уже имеющийся probe, но ABI-независимость потребует заголовков); VLD необязателен, если oracle будет верифицирован.
3. Для проверки преобразования *Encoded→native* нужны доказанные трассы конкретных защищённых op_array, соответствующие источники или достаточные контрольные образцы одной версии кодировщика (код защищённых файлов не исполнять).
4. Для семантической проверки PHP-кандидатов нужен согласованный безопасный метод; по текущим ограничениям **их запуск запрещён**.

**Семантическая эквивалентность не доказана**; синтаксическая проверка и числовое распознавание не заменяют её.
