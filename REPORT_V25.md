# Zend Decompiler v25 — сохранённые трассы и read-only dataflow

## Область выполненной работы

Выполнена статическая **повторная проверка ранее сохранённых** трасс native-opcode handler probe относительно закодированной сериализации. Никаких защищённых PHP-файлов, восстановленных кандидатов, Zend Optimizer или серверных исполняемых файлов в этом шаге **не запускалось**. Исключение — **собственный** тестовый PHP-файл `corpus/own_sources/02_foreach.php`: он только скомпилирован командой PHP 5.2 `-n -l` с ранее созданным диагностическим расширением (без исполнения тела программы).

Программная логика восстановления и таблица `opcode_map_observed_v20.json` **не изменены**. Добавлены два независимых, не генерирующих PHP инструмента:

- `zend_alignment_audit.py`: сравнивает сериализованные записи с **историческими логами**, проверяет число групп, порядок функций, длины, номера исходных строк, однозначные кандидаты обработчиков; требует явного свидетельства и отдельной аннотации для двух сдвигов после `FE_FETCH`. При несовпадении формы потока **отказывает**, не выравнивает произвольно.
- `zend_readonly_dataflow.py`: типизированные operand-представления (`constant`, `compiled_variable`, `temporary`, `variable_temp`, `unused`) и чисто синтаксический reaching-definitions по существующему CFG. Не заменяет выражения, не восстанавливает PHP, не считает синтаксическую уникальность доказательством семантической эквивалентности.

Добавлены CLI-команды `dataflow` и `align-archived`, 7 новых автоматических тестов; кодировка и набор старых соответствий не изменены. Версия `zend_engine` помечена как 25; отличается только версия в заголовке генерации, допускаемая golden-тестом.

## Результат аудита сохранённых трасс

Команда:

```bash
python zend_cli.py align-archived --data-root /mnt/data -o alignment_audit_v25.json
```

**Источник доказательства ограничен**: старые диагностические логи содержат трассы предыдущих исследований, их происхождение и обработчики не были независимо заново аттестованы этим шагом. Это **не** независимый эталон из оригинала Zend Encoder и **не** round-trip.

- 6 входных закодированных файлов, 34 группы, 4204 сериализованные инструкции, 295 наблюдаемых ключей.
- 4099 совпадений с архивными однозначными handler-ID без сдвига; 81 совпадение после явного выравнивания двух `foreach`-случаев.
- 18 записей имеют эмпирическое соответствие `140`, но смысл такого соответствия конфликтует с контекстом или не подтверждён; **не** считать их подтверждёнными DECLARE_INHERITED_CLASS.
- 2 инструкции с ключом `1:199` остаются **неизвестными** (`out_price #65`, `uc_rus #17`).
- 2 случая имеют неустановленный handler-ID в архивных трассах (ключ `3:9`); нативная нумерация сама по себе не компенсирует отсутствие однозначного наблюдения.
- 2 **реальных несовпадения** действующего отображения: ключи `3:139` и `6:236` сопоставлены в таблице с native `66` (`SEND_VAR`), но один архивный пример для каждого указывает на `65` (`SEND_VAL`). Старый вспомогательный код содержит условную обработку по типу аргумента, но **действующая** таблица не активирует её. Ни один из двух ключей не переименован автоматически, чтобы не нарушить golden и не ввести неподтверждённую семантику. См. `alignment_audit_v25.json`.

Показатели выше — **классы наблюдений в архивных логах**, а не количество семантически восстановленных инструкций.

## Собственный контролируемый пример

Команда (локальные пути к PHP 5.2 и ранее созданному диагностическому расширению):

```bash
LD_LIBRARY_PATH=/mnt/data/php52_libs ./php52_linter -n \
  -d zend_extension=/mnt/data/zend_work/probe_with_cv.so \
  -l corpus/own_sources/02_foreach.php
```

Полученные opcode IDs: `[71,72,38,77,78,137,38,40,42,49,62,149]`. Нормализованный результат побайтово на уровне JSON-данных совпадает с `corpus/compile_only_dumps/02_foreach.normalized.json`. `FE_RESET=77`, `FE_FETCH=78`, `SWITCH_FREE=49` относятся к native opcode-ID этого PHP 5.2, **не** к неразрешённому сериализованному ключу `1:199`.

**Round-trip: `not_run`.** В имеющихся материалах не найден проверенный Zend Encoder для кодирования собственных контрольных PHP-программ в совместимый поток `SSG Team`. Имеется Zend Optimizer (декодирующая сторона), но не Encoder (кодирующая сторона). Входной формат `zend_serial_parser.py` отличается от нативного дампа `op_array`, поэтому прямую подстановку делать нельзя.

## Диагностика `fun_all.php`

Команда:

```bash
python zend_cli.py dataflow sample_inputs/fun_all.php -o readonly_dataflow_fun_v25.json
```

Функция `out_link()`: инструкция `#16` в CFG-блоке `B016` читает TMP-ячейку `[2,0,0]`, имеющую **две синтаксически достижимые точки определения**: `#13` (`JMPZ_EX`) и `#15` (`BOOL`). Это короткозамкнутая логическая конструкция, при этом первое сравнение использует результат вызова функции. Текущий `join_proofs()` намеренно принимает только строго доказанные чистые сравнения и не строит из этой цепочки выражение. Подмена любой из точек определения небезопасна. `readonly_dataflow_fun_v25.json` не содержит исполняемого PHP.

`out_price()` и `uc_rus()` отмечены `unsupported` для read-only CFG из-за неизвестного `1:199` — никакого dataflow-псевдодоказательства для них не создаётся.

## Ограничения и необходимые данные

- **Нужен совместимый Zend Encoder** или проверенная пара «собственный тестовый PHP → закодированный `SSG Team`», созданная именно использованным Encoder. Без этого независимое соответствие опкодов и честный round-trip остаются заблокированными.
- Разбор полученных архивных диагностических логов не заменяет проверенную первичную пару. Инструкции `140`, `1:199`, неоднозначные `SEND_VAL`/`SEND_VAR` нельзя считать разрешёнными.
- Нужны доказательства alias/side-effect semantics, прежде чем read-only reaching definitions можно применять для подстановок в PHP.
- В новой итерации исходный PHP-код сайта **не исполнялся**. Восстановленные PHP-кандидаты **не исполнялись** (только синтаксис). Семантическая эквивалентность **не доказана**.
