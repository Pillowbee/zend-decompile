# Независимый аудит Zend Decompiler v25 → v26

## Метод и границы

Основание — исходный архив `zend_decompiler_stage25.zip` и дополнительно приложенный
`files.zip`. Сначала выполнены распаковка без выхода за пределы директории,
статический обзор импортов и тестовых команд, независимый SHA-256 golden/manifest;
затем исходные 43 unittest и baseline batch, и только после этого изменения.
Закодированный PHP не исполнялся и не передавался PHP-интерпретатору. Загруженные
`php` и `ZendOptimizer.so` определены только статически как x86-64 ELF, не запускались
и в v26 не включены. Дополнительный `files.zip` содержит заголовки Zend;
`zend_vm_opcodes.h` побайтово идентичен комплекту `reference_headers_php52_candidate/`.
Это не доказывает совпадение версии с PHP 5.2.17 и не связывает native opcode с Encoder.

## Архитектура, полученная из AST импортов

- CLI (`zend_cli`) → движок (`zend_engine`) или пакетный обработчик (`zend_batch`),
  либо отдельные read-only анализаторы.
- `zend_engine` → разбор сериализации (`zend_serial_parser`), эмпирическая таблица
  (`zend_calibrate_v9`), восстановление (`zend_restore_core`), optional isolated parser.
- `zend_restore_core` → CFG (`zend_cfg_v11`), `zend_crossblock_v17`, `zend_state_v19`,
  `zend_structure_v17`, `zend_prefix_restore_v17` (исторические имена файлов не
  означают использование устаревших точек входа).
- `zend_readonly_dataflow` отдельно читает бинарную сериализацию, таблицу и CFG;
  по умолчанию он **не участвует** в генерации PHP. Исправления v26 относятся к этому
  ядру диагностического dataflow/IR, не к PHP-эмиттеру.
- `zend_compiler_oracle` разбирает compile-only native-дампы **собственных** PHP
  фикстур. Адаптера native `op_array` → SSG Team serialized stream нет.

AST обнаружил 28 Python-модулей верхнего уровня и 60 рёбер импортов между ними.

## Golden и регрессия

`golden/v20/manifest.json`: 11 исходных входов имеют совпадающие SHA-256; словарь
и таблица соответствуют манифесту; все **16** эталонных code/audit-файлов
побайтово соответствуют индивидуальным SHA-256 из манифеста.
Golden-сравнения и повторный вызов v20 восстановителя успешно проходят тесты.
Факт совпадения байтов — тест регрессии, **не** доказательство правильного PHP.

v25: `python -m unittest discover -s tests -v`: 43/43 без ошибок, 2 пропуска.
Пакетный запуск v25 с `--isolate-parser`: 11 входов → 8 `candidate_generated`,
2 `unsupported`, 1 `not_encoded` (код завершения 2 ожидаем).
Из отказов не получено исполняемых `.php`. Дополнительная PHP syntax/semantic
валидация **не производилась**: `-l` не является доказательством эквивалентности.

v26: `python -m unittest discover -s tests -q`: 49 тестов, 0 failures/errors,
2 skips; тот же batch 8/2/1, нормализованное по метке версии содержимое 8
кандидатов сопоставлено с golden. Более старый `validation_v23.py`, запущенный
как дополнительный тест исторических отчётов, **не завершился в пределах времени
запуска**; он не засчитан как успешный. Матрица Python 3.10–3.12 здесь не запускалась;
основной прогон выполнен на Python 3.13.

## Zend Encoder opcode map — уровень доказательств

Наблюдательная таблица содержит 313 ключей и 50 разных native-ID. Сохранённое
`opcode_evidence_v21.json` содержит 314 записей: 305 `inferred`, 9 `unknown`,
**0 `confirmed`**. Заголовок семейства PHP 5.2 показывает native-значения
`SWITCH_FREE=49`, `SEND_VAL=65`, `SEND_VAR=66`,
`DECLARE_INHERITED_CLASS=140`, но не подтверждает их соответствие сериализованным
байтам Encoder. Синтаксическая проверка имён таблицы по предоставленному заголовку
не выявила разногласий для сопоставимых именованных native-ID; это не независимая
верификация формата Encoder.

Отчёт `alignment_audit_v25.json` утверждает 4204 архивно выровненных инструкций,
2 несоответствия для ключей `3:139` и `6:236`, 2 неизвестных `1:199`,
18 сомнительных контекстов native-ID 140. **Эти результаты невозможно независимо
повторить**: первичные исторические трассы не включены в архив. Поэтому вывод о
2 несовпадениях классифицируется как *подозрение по архивному артефакту*, а не
доказанная семантика. Соответствия `3:139`, `6:236`, `1:199`, и `140` **не менялись**.

## Воспроизводимые ошибки v25 и исправления v26

**Ошибка A: пропущено определение на back-edge B000.** Синтетический цикл читает
TMP[0] в инструкции #0, определяет TMP[0] в #1, из #2 прыгает к #0. Реальный
набор достигающих определений для #0: `[-1, 1]` (`-1` означает первый вход без
определения). v25 выдавал `[-1]` с `no_reaching_definition`, потому что
`union_predecessors('B000')` безусловно сбрасывал всех предшественников.

**Ошибка B: ложная неопределённость из-за прогрева fixed point.** На другом
синтетическом цикле TMP[0] безусловно определяется в #0 до цикла и читается в #2.
Правильный ответ `[0]`; v25 выдавал `[-1, 0]` — временно пустые состояния
предшественников ошибочно превращались в семантическое `undefined` и оставались
в цикле при последующих итерациях.

**Исправление:** перечисляются реальные TMP/VAR слоты; только виртуальный вход в
B000 вводит sentinel `-1`. Join по предшественникам использует пустое множество
как `bottom` до завершения fixed point, без искусственного `-1`. Реальные CFG
back-edges в B000 учитываются. Оба контрпримера находятся в `tests/test_v26_soundness.py`
и теперь дают `[-1,1]`/`[0]`, соответственно.

**Ошибка уверенности CFG:** v25 read-only dataflow строил CFG для распознанного
как native-ID `140` в `links_fun(1).php` (`<main>` #14, encoded key `6:226`),
несмотря на статус `unknown` в собственном evidence. v26 сверяет хеши mapping,
metadata, evidence и отказывает таким группам без подстановки PHP-опкода.
Для `fun_all.php` поддерживаются 15/23 групп read-only dataflow (8 `unsupported`),
для `links_fun(1).php` 4/6 (2 `unsupported`) вместо прежних 21/23 и 6/6.
Это **корректировка достоверности**, а не ухудшение распознавания на нативных дампах.

## Причины невозможности полного восстановления

- `fun_all.php`: в `out_link` #16 TMP `[2,0,0]` имеет два синтаксически
  достигающих producer (#13 `JMPZ_EX`, #15 `BOOL`); автоматически выбирать один
  нельзя. В `out_price` #65 и `uc_rus` #17 встречается неизвестный key `1:199`.
  В ряде других групп используется спорный native-ID `140`, и есть
  неаттестованные межблочные alias/side-effects.
- `links_fun(1).php`: в `<main>` инструкция #12 — `SEND_VAR` при отсутствии
  локально установленного состояния открытого вызова; в #14 находится
  key `6:226`, которому старая таблица сопоставляет сомнительный `140`.
  Исправление только call stack без независимого доказательства #14 небезопасно.
- Для обоих файлов нужен проверенный Encoder-контур на **собственных** фикстурах,
  исходные диагностические трассы, и строгие доказательства структуры `op_array`
  и семантики опкодов перед восстановлением исполняемого кода.

## Чего v26 НЕ делает

Не добавляет и не подменяет opcode, не меняет golden, не исполняет предоставленный
или сгенерированный PHP; не заявляет round-trip или доказанную семантическую
эквивалентность. Старый PHP-эмиттер остаётся экспериментальным; его 8 кандидатов
не являются готовым к эксплуатации PHP. Нужен отдельный проверенный oracle прежде,
чем расширять восстановление `fun_all` или `links_fun`.
