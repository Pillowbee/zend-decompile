# Технический отчёт: Zend Decompiler v21.0.0-experimental

**Состояние:** завершена ограниченная инженерная итерация v21, **не** завершён весь многoэтапный план. Исходный Zend-код не исполнялся; PHP 5.2 использовался только в режиме `-n -l` для синтаксиса кандидатов. Полная эквивалентность восстановленных программ оригиналам не доказана.

## Этап 0 — эталон до изменений

- Сначала скопирован исходный v20 в отдельный каталог, затем **до правки исходников** получены `golden/v20`: 8 полных PHP-выводов, 8 исходных аудитов v20, манифест SHA-256 всех 11 образцов, SHA-256 словаря и карты, 2 отчёта о незавершённых группах.
- `tests/test_golden.py` проверяет точные входные SHA-256, идентичность кода и аудитам v20 и сравнение v21 с эталоном за исключением **одного заголовка версии**. Проверки прошли.

## Направление 1 — проверка корректности

**Реализовано:** девять проверок, включая golden, безусловный отказ на неподдерживаемом коде, бинарный корпус с ~100 детерминированными повреждениями/усечениями, невозможность перезаписи файлов. Опциональная проверка синтаксиса PHP 5.2 выполнена для восьми кандидатов; все восемь прошли.

**Не реализовано:** round-trip опкодов (`not_run`), оригинальный PHP → op_array → восстановитель (`not_run`), property-based генерация через Hypothesis, систематические memory/time budgets. Старые динамические тесты v15–v19 **не запускались** из-за жёсткого запрета на выполнение предоставленного PHP-кода. Для надёжного round-trip нужен проверенный дизассемблер/дамп опкодов PHP 5.2.17, сопоставление функций и нормализатор CV/TMP/VAR, а также исходный адаптер формата. Наличие в рабочей среде бинарного PHP 5.2 не доказывает наличие корректного VLD.

## Направление 2 — опкоды и неоднозначность

**Реализовано:** `opcode_evidence_v21.json` с SHA-256 привязанной эмпирической таблицы и состояниями `confirmed/inferred/unknown`. Все 313 числовых соответствий **не подтверждены независимыми ключевыми источниками** и помечены соответственно: `inferred` для обычных и `unknown` для семантически сомнительного `140`. `1:199` остаётся `unknown` (для `out_price` и `uc_rus`), а `49` остаётся предположительным. Аудит различает числовое распознавание и статус уверенности; 0 ключей `confirmed`.

**Не реализовано:** строгая сверка с `zend_compile.h` и `zend_vm_def.h` **точно того** PHP 5.2.17 build, полученного для экспериментов. Гипотеза по `140`: формальный код PHP 5.2 означает `DECLARE_INHERITED_CLASS`, но местоположение внутри серии передач аргументов даёт несовместимый контекст; без первичного опкодно-знакового дампа подстановка альтернативной инструкции запрещена. План проверки: маленький открытый тест PHP + отдельный проверенный compile-only handler probe + независимое чтение исходников Zend Engine; затем целевая сверка контекста.

## Направление 3 — ядро восстановления

**Сделано:** в `zend_restore_v19.restore(..., version=...)` введена параметризованная версия, устранён `bytes.replace` из копии v20. Проверено, что семантическое тело и исходный v20 API не изменены. **Текущие алгоритмы структурирования и `while/switch` не перерабатывались.**

**Оценка IR:** `zend_prefix_restore_v17.Decoder` хранит выражения как байтовые строки, `zend_structure_v17` перестраивает области CFG, `zend_state_v19` — fail-closed fallback. Немедленный полный переход на AST/типизированный IR нарушил бы накопленные локальные предположения: нужен постепенный переход через объекты `Operand/Expr/Stmt`, адаптер вывода старого форматирования, новые golden тесты на каждом шаге. Основная причина отказов — межблочная передача временных значений и неразрешённый контекст FE_RESET/FE_FETCH, а не только формат выражений. Поддержка исключений, универсального foreach, `list`, `isset/empty` и улучшенное структурирование откладываются.

## Направление 4 — диагностика отказов

**Реализовано:** у каждой неудачи есть отдельный статус, сообщение, SHA-256 и отчёт числового распознавания; для неизвестных ключей — индекс опкода и окно `±2`, для отказа внутри CFG — **предположительный старт проблемного блока** с окном, без утверждения точного места дефекта. В пакетном режиме неподдерживаемые исходники не заменяются исполняемыми PHP-файлами. `zend_partial.py` помещает доступные групповые результаты в `.txt`, с предупреждением `/* UNRECOVERED */`, без PHP open tag. Кодовые группы обозначены `candidate fragment`, но их семантическая правильность не доказана.

## Направление 5 — инженерия

**Реализовано:** `RestoreResult` (status/code/audit/reason), `zend_engine.py`, `zend_batch.py`, `zend_cli.py`, `zend_partial.py`; встроенные метаданные версии, SHA-256 входа/словаря/таблицы/доказательств, best-effort структурные диагностики, атомарная запись с отказом от перезаписи, 4 подкоманды CLI, `pyproject.toml`, два JSON Schema, CI workflow c Python unit tests. Wheel собран и успешно запущен из изолированного окружения с доступной зависимостью networkx.

**Не сделано:** реальное объединение старых внутренних модулей v15–v20 в один новый typed backend и импорт старой Git-истории; в архиве сохранена старая цепочка реализаций. Настоящие тесты legacy v15–v19, исполняющие PHP, нельзя включить в CI без нарушения ограничений задачи. CI workflow написан, но его запуск в GitHub Actions **не проводился**. Изоляцию таймаута/памяти парсера на уровне OS пока нужно расширить; атомарность двух выходных файлов не является полноценной ACID-транзакцией.

## Проверки и команды

```bash
cd zend_decompiler_v21
python zend_cli.py validate
python zend_cli.py batch sample_inputs -o examples/batch_v21 \
  --php-linter /ABSOLUTE/PATH/TO/php52_linter \
  --lib-dir /ABSOLUTE/PATH/TO/php52_libs
python zend_cli.py audit 'sample_inputs/fun_all.php' > /tmp/fun_all_audit.json
python zend_cli.py restore sample_inputs/basket.php -o /tmp/basket_candidate.php --audit /tmp/basket_candidate.json
```

`batch` ожидаемо возвращает код `2` при двух unsupported файлах. PHP-кандидаты НЕ запускаются. `php52_linter` не входит в ZIP-дистрибутив; при необходимости он должен предоставляться пользователем.

Регистрируемые индексы блоков — начальные, не обязательно точная инструкция нарушения. `opcode=140` остаётся неоднозначным.

## Приоритет следующей итерации

1. Верифицировать PHP 5.2.17 opcode reference/handler dump и смысл `140`, `1:199` без угадываний.
2. Построить отдельный адаптер compiler op_array → внутренний сериализованный IR на открытых собственных примерах; только затем включить round-trip и эталонный корпус.
3. Ввести типизированные временные значения и консервативное dataflow между базовыми блоками на ограниченных инструкциях и golden-тестах.
4. Добавить в тестирование проверяемый бюджет времени/памяти и репродуцируемые fuzz-файлы.
