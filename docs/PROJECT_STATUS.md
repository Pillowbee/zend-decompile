# Zend Decompiler v28 — актуальное техническое состояние

Этот документ — **единый технический ориентир для сопровождения и развития** текущего кода. Команды для пользователя находятся в [README](../README.md). Устаревшие отчёты итераций удалены из рабочей ветки, но остаются в Git history. Здесь разделены *подтверждённое регрессионными проверками*, *наблюдаемые диагностические свидетельства* и *нерешённые гипотезы*. Информация относится к состоянию проекта после консолидации 22.10.2026; дальнейшие изменения требуют повторного измерения.

## 1. Что делает проект и чего он не гарантирует

- Поддерживает ограниченный набор сериализованных Zend Encoder / PHP 5.2-файлов; это **не** произвольный PHP-байткод и не универсальный декодер ionCube/Zend.
- Возвращает `candidate_generated`, `unsupported` либо `not_encoded`. При непроверенном потоке управления/операндах должен **отказывать** (`fail closed`), а не выводить частичный PHP как законченный.
- Кандидат PHP, его синтаксическая валидность и совпадение с golden **не равнозначны** поведенческой эквивалентности исходной программы. Никакого подтверждённого source → encoded Zend stream → decompiled source round-trip пока нет.
- Недоверенный/защищённый PHP и восстановленные кандидаты **не исполнять**. Допускается только статический разбор, а для синтаксиса — отдельно согласованный PHP `-n -l` без исполнения. `--isolate-parser` ограничивает первичный разбор на Linux, но не является общей песочницей.

## 2. Актуальная архитектура и структура исходников

Рабочий код упакован как стандартный Python-пакет `src/zend_decompiler/`; **в корне нет исполняемых Python-модулей**. Импорты внутри пакета относительные, для запуска из исходников достаточно зависимости из `requirements.txt` и переменной `PYTHONPATH=src`. `pyproject.toml` определяет entry-point `zend-decompiler = "zend_decompiler.cli:main"`; альтернативный запуск — `python -m zend_decompiler`.

```text
src/zend_decompiler/
  __init__.py, __main__.py   публичный Python API и модульный запуск
  cli.py ────────────────> engine.restore_result() [единая точка восстановления]
   │                         ├── serial_parser.py (+ parser_isolated.py)
   ├── batch.py              ├── calibrate.py (+ evidence из data/opcodes/)
   │                         └── restore_core.py
   │                              ├── prefix_restore.py [выражения/TMP/VAR]
   │                              ├── cfg.py [CFG], crossblock.py [связи]
   │                              └── structure.py, state.py [эмиссия]
   └── readonly_dataflow.py, triage.py, ir_evidence.py [read-only]
  assets.py                  пути к словарю, карте, тестовым эталонам
  block_previews.py, research.py, fuzz.py, alignment_audit.py,
  header_audit.py, compiler_oracle.py, partial.py [исследования]
data/opcodes/, data/research/ данные отдельно от Python-кода
tests/, golden/reference/     неизменённые регрессионные объекты
sample_inputs/, corpus/       испытательные входы и собственные фикстуры
```

Публичный API: `zend_decompiler.restore_result()`, `zend_decompiler.RestoreResult`; реализация в `zend_decompiler.engine`. Исследовательские CLI запускаются как `python -m zend_decompiler.<имя_модуля>` (например, `zend_decompiler.triage`), а не исполнением внутренних файлов по абсолютному пути. Изолированный парсер также использует `-m zend_decompiler.parser_isolated`.

Тесты импортируют только `zend_decompiler.*`. Работа ведётся с актуальным исходным деревом: для проверки используются локальные `unittest` и обработка `sample_inputs/`. Обратная совместимость с прежними API и CLI-обёртками не требуется.

## 3. Единственные показатели успешности

Прогресс разработки измеряется **только двумя числами**:

| Показатель | Последнее локальное измерение |
|---|---|
| **Успешно пройденные автоматические тесты** | **79** из 82 (3 пропущены) |
| **Количество полностью обработанных закодированных PHP-файлов** | **8** из 11 входов со статусом `candidate_generated` |

Получение обоих показателей напрямую из исходного дерева:

```bash
python -m pip install -r requirements.txt
export PYTHONPATH=src
python -m unittest discover -s tests -q
python -m zend_decompiler batch sample_inputs -o /tmp/zend_batch --isolate-parser
```

`unittest` сообщает количество пройденных и пропущенных тестов; `batch` выводит `generated`, `unsupported` и `not_encoded`. В число обработанных файлов входят **только `generated`**, а не диагностические блоки, частичные результаты и незакодированные файлы. На текущем наборе два файла имеют статус `unsupported`, один — `not_encoded`. Полученный PHP по-прежнему *кандидат*, не аттестованный оригинал.

**Обратная совместимость между выпусками проекта не является требованием**: прежние API, CLI, внутренние структуры и форматы выходных данных могут изменяться. Golden-образцы остаются тестовыми ожиданиями текущей реализации и могут пересматриваться вместе с алгоритмом; нельзя менять тесты и эталоны исключительно ради увеличения показателя успешных тестов.

## 4. Уровни достоверности opcode

- Активная карта: `data/opcodes/opcode_map.json`, метаданные `data/opcodes/opcode_map.json.meta.json`, provenance: `data/opcodes/opcode_evidence.json`, гипотезы: `data/opcodes/opcode_map.json.meta.json (поле `hypotheses`)`, словарь: `zend_verified_dictionary.bin`.
- По сохранённому аудиту: **313** эмпирических ключей, **305 inferred / 9 unknown / 0 confirmed** evidence-записей. Имя native opcode в таблице не означает, что сопоставление с ключом Encoder подтверждено независимой трассой.
- Не смешивать **native opcode ID** и **сырой ключ сериализации** вроде `1:199` (`позиция:значение`). Отсутствие native opcode 199 не объясняет ключ `1:199`.
- Сохранённые заголовки в `reference_headers_incompatible/` относятся к более современному Zend Engine и **не подходят** как источник PHP 5.2. Набор `reference_headers_php52_candidate/` согласуется с *семейством* PHP 5.2, но точное происхождение из PHP **5.2.17 не удостоверено**; дополнительно см. `data/research/header_audits.json (`records.php52_family`)` / `data/research/header_audits.json (`records.incompatible_headers`)`.
- В кандидате заголовков семейства PHP 5.2: native `49 = ZEND_SWITCH_FREE`, `140 = ZEND_DECLARE_INHERITED_CLASS`; номер 199 там не определён. **Это не позволяет** назначать смысл сериализованному ключу `1:199` либо эмпирическому ключу, отнесённому таблицей к числу 140.
- `data/research/alignment.json` содержит архивное выравнивание и подозрения по `3:139`, `6:236`; исходные исторические трассы отсутствуют, поэтому эти выводы нельзя считать независимо подтверждёнными. Переприсвоение opcode без новых проверяемых свидетельств запрещено.

## 5. Конкретные нерешённые файлы

### `sample_inputs/fun_all.php` — unsupported

- Неизвестный ключ `1:199` наблюдается в `out_price` на инструкции **#65** и `uc_rus` на **#17**. Обе позиции имеют одинаковое локальное окно ключей `7:98, 0:24, 1:199, 2:42, 3:9` и совместимые типы операндов. Это корреляция, **не** определённая семантика. Read-only артефакт: `data/research/analysis.json (`records.source_anchored_ir`)`.
- В `out_link` чтение `TMP[2,0,0]` на **#16** имеет два синтаксически достижимых producer: **#13** (`JMPZ_EX`) и **#15** (`BOOL`). Путь, достижимый в CFG, не обязательно выполним при реальных значениях. Выбирать один producer и сворачивать в `&&` или `||` нельзя.
- Аналогичные предполагаемые CFG-слияния наблюдались в `currency_type` (#5/#8→#9), `out_field` (#28/#31→#32); автоматическая реконструкция условных выражений ещё **не доказана**.
- В сохранённом triage `data/research/analysis.json (`records.triage`)`: **23 группы**, из которых **15** поддаются синтаксическому read-only анализу; это не 15 семантически восстановленных PHP-функций. Новые диагностические блоки также не дают оснований выпускать полный кандидат.

### `sample_inputs/links_fun(1).php` — unsupported

- В `<main>` на **#12** есть `SEND_VAR` без надёжно восстановленного состояния открытого вызова.
- На **#14** сериализованный ключ `6:226` сопоставлен эмпирической картой со спорным native ID **140**; трактовка как `DECLARE_INHERITED_CLASS` **не подтверждена**.
- В сохранённом triage `data/research/analysis.json (`records.triage`)`: **6 групп**, **4** поддаются ограниченному синтаксическому анализу; без подтверждения контекста вызова/семантики opcode полный PHP запрещён.

## 6. Подтверждённые инженерные решения

- CFG: `EXIT = 79` является терминальным native opcode (обычное продолжение отсутствует); неподтверждённые рёбра для `BRK/CONT/FE_RESET/FE_FETCH/CATCH/THROW` должны приводить к консервативному отказу, а не к фиктивному fallthrough. **Native** семантика не подтверждает автоматически **Encoder** mapping.
- Синтаксический reaching-definitions обрабатывает back-edges и вход `undefined` отдельно. Для чтения с несколькими возможными определениями сохраняет неоднозначность; не удаляет `undefined` и не генерирует фиктивный литерал.
- Синтетическая ограниченная независимая проверка: **300/300** коротких CFG совпали между fixed-point и BFS-эталоном. Это свидетельство против локальных багов, но не всеобщее доказательство.
- `src/zend_decompiler/compiler_oracle.py` читает **compile-only native op_array** для *собственных* фикстур из `corpus/`. Адаптера native `op_array` → формат `SSG Team` и настоящего подтверждённого round-trip **нет**.
- Read-only инструменты должны сохранять контекст ошибки (operand-type, instruction index, путь, лимиты бюджета), не писать строковые литералы PHP/секреты и не воздействовать на PHP-эмиттер.

## 7. Приоритеты дальнейшего развития

1. **Доказательство соответствий:** получить воспроизводимые пары только собственных PHP 5.2 исходников, их достоверных *encoded serialized* потоков и независимых native compile-only трасс **той же версии**. Подтвердить происхождение PHP 5.2.17 заголовков. Только после этого проверять `1:199`, ключи, связанные с 140, `3:139`, `6:236` и контексты `FE_FETCH`.
2. **Структура вызовов и TMP:** воспроизвести и покрыть отрицательными тестами `SEND_VAR`/call-state для `links_fun(1).php` и двузначные TMP-слияния `fun_all.php`. Устанавливать уникальность producer/side effects по доказательствам; иначе `unsupported`.
3. **Постепенный типизированный IR:** добавить `Operand`/`SourceSpan`, ограниченный `Expr/Stmt` и последовательно расширять поддерживаемые конструкции PHP. Сохранение побайтового вывода прежних выпусков не обязательно.
4. **Тесты нового обработчика:** добавлять позитивные и отрицательные случаи, понятную диагностику отказа и проверять изменение числа полноценно обработанных файлов. Пересматривать эталоны вместе с обоснованными изменениями алгоритма, а не ради формального прохождения тестов.
5. **Воспроизводимость измерений:** локально запускать одинаковый набор тестов и обработку одних и тех же PHP-образцов. Отчитываться только о количестве успешных тестов и числе полностью обработанных файлов, не подменяя реальные результаты неподтверждёнными фрагментами.

## 8. Каталог JSON-данных и их роль

В корне проекта **нет JSON-файлов**. Активные данные и важные исследовательские отчёты сгруппированы в `data/` под именами, **не зависящими от версии выпуска**.

| Файл | Что содержит и зачем нужен | Использование |
|---|---|---|
| `data/opcodes/opcode_map.json` | Эмпирическая карта циклических ключей Zend Encoder → предполагаемые native opcode. SHA-256 исходного файла сохранён. | **Обязателен** для декодирования; `zend_decompiler.assets.OPCODE_MAP`. |
| `data/opcodes/opcode_evidence.json` | Отдельные свидетельства и уровни достоверности для ключей карты. SHA-256 исходного файла сохранён. | **Обязателен** для проверки уверенности и fail-closed контроля. |
| `data/opcodes/opcode_map.json.meta.json` | Контрольные SHA-256 карты/evidence, атрибуты формата и ранее отдельные неподтверждённые `hypotheses.issues`. | **Обязателен** для проверки согласованности; `zend_decompiler.assets.OPCODE_METADATA`. |
| `data/research/alignment.json` | Архивная сверка 4204 инструкций с внешними трассами, включая конфликты. Исходный JSON сохранён побайтово. | **Тестовый эталон** `zend_decompiler.assets.ALIGNMENT_FIXTURE`; не используется генератором PHP. Не является независимым oracle. |
| `data/research/analysis.json` | Объединяет `records.source_anchored_ir`, `records.triage`, `records.readonly_dataflow_fun`, `records.readonly_dataflow_links`, `records.own_foreach_compile_check`. | **Read-only исследовательский архив**: анализ неизвестных ключей, TMP/VAR и собственных compile-only фикстур. Не используется PHP-эмиттером. |
| `data/research/header_audits.json` | Объединяет `records.php52_family`, `records.incompatible_headers`, `records.comparison_summary`; различает старый кандидат заголовков и несовместимые современные. | **Исследовательский архив**, не активная таблица Encoder. |

Оба объединённых исследовательских файла содержат `schema_version`, `records`, `source_integrity`: исходные SHA-256 отдельных файлов и проверяемые SHA-256 нормализованных вложенных объектов. `tests/test_data_layout.py` сверяет структуру, привязки к активным данным и хеши объектов. Имена первоначальных JSON с `vNN` сохранены только в прежних Git-коммитах; поля версии, встречающиеся **внутри** неизменённых исторических свидетельств, означают происхождение данных, а не требование к версии движка.

Почему **не** слиты три активных opcode-файла: у карты, evidence и metadata различные проверяемые схемы; карта и evidence взаимно связаны SHA-256, а объединение изменило бы их байты и нарушило независимую golden-регрессию. Гипотезы, не являвшиеся самостоятельным исполняемым источником, безопасно включены в metadata.

Из корня удалены историческая карта `opcode_map_observed_v10.json`, серия снимков `validation_v19.json`–`validation_v28.json` (по существовавшим выпускам), а также `user_audit_v19.json` и `user_differential_v19.json`. Эти файлы не импортировались текущими скриптами/тестами и служили отчётами прошлых запусков. Их можно восстановить из Git history; действующие локальные тесты и проверяемые эталоны являются источником текущего статуса, а не старый `validation_vNN.json`.

JSON в `golden/reference/`, `corpus/`, `schemas/` и `tests/` сохранены. Старые пакетные отчёты и аудиты `examples/batch_v*` исключены из рабочей ветки; единственный исторический `batch_report.json` перенесён побайтово в `tests/fixtures/` для проверки схемы. Относительные ссылки внутри старого отчёта не являются действующими файловыми путями.

## 9. Критерии развития

1. Исходные PHP-образцы оставлять контрольным набором входов для сопоставимого подсчёта. Данные, opcode-карту и эталоны можно обновлять вместе с развитием алгоритма, но не для искусственного увеличения числа пройденных тестов.
2. При изменении формата `data/opcodes/` согласованно обновлять декодер, проверку SHA-256, тесты и документацию. Поддержка прежнего формата не обязательна.
3. Для новых исследовательских данных добавлять смысловые имена, проверяемое происхождение и актуальные тесты; не возвращать разрозненные старые отчёты в корень проекта.
4. Оценивать развитие только числом пройденных тестов и числом файлов со статусом `candidate_generated`. Архивные гипотезы не превращать в подтверждённые правила автоматически.

## 10. Правила размещения нового кода

1. Новые исполняемые Python-модули размещать только в `src/zend_decompiler/`; импортировать внутри пакета относительно (`from .assets import …`).
2. Для общих команд расширять `cli.py` и публичный `__main__.py`, не добавлять новые скрипты в корень.
3. Тесты хранить в `tests/`, данные — в `data/`, `corpus/`, `golden/`; внутренние форматы и текущие эталоны допускается обновлять без обязательства сохранять поведение прежних выпусков.
4. После изменений локально запускать `python -m unittest discover -s tests -v` и `python -m zend_decompiler batch sample_inputs -o /tmp/zend_batch --isolate-parser`; фиксировать два показателя: пройденные тесты и полностью обработанные файлы.
5. Изменение модульной структуры не является новым подтверждением семантики Zend Encoder: неизвестные opcode и отсутствие round-trip остаются ограничениями.

## 11. PHP-артефакты: единый эталон вместо версионных копий

В 74 прежних PHP-файлах найдено **38 дублирующих выходов декомпилятора**: они точно совпадали с существующими golden-кандидатами либо отличались **только комментарием о версии**. Удалены повторные PHP из `examples/batch_sample_outputs/`, `examples/batch_v21/`, `examples/batch_v22/`, `examples/batch_v23/`, `generated/` и `user_candidate_v19.php`. Исторические JSON-аудиты этих запусков тоже удалены из текущего дерева; содержимое по-прежнему доступно из Git history.

| Путь | PHP-файлов | Назначение |
|---|---:|---|
| `sample_inputs/` | 11 | Защищённые входные файлы; **не исполнять** и не изменять. |
| `golden/reference/code/` | 8 | Текущие эталоны PHP-кандидатов; можно обновлять при изменении алгоритма. Не доказывают семантическую эквивалентность. |
| `corpus/own_sources/` | 5 | Собственные PHP-фикстуры для compile-only исследования. |

Файлы `research/fragments/` — **экспериментальные**, и историческое имя каталога `fun_all_validated_fragments` не означало доказанной поведенческой эквивалентности. Сгенерированный PHP не запускать.

`tests/fixtures/batch_report.json` — исторический, побайтово сохранённый batch-отчёт для JSON-schema regression. Относительные пути к выходным `.php` и `_audits/` в нём описывают **удалённый архивный запуск**, не живые файлы. Для текущего результата запустите `python -m zend_decompiler batch sample_inputs -o /tmp/zend_batch --isolate-parser`.

Новый тест `tests/test_php_artifacts.py` проверяет отсутствие дубликатов, в том числе после удаления из хешируемых данных комментария версии. `.gitignore` защищает от случайного добавления папок со вновь сгенерированными выводами. Для экспериментов указывайте выходной каталог **за пределами Git-репозитория**.
