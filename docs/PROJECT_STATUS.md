# Zend Decompiler v29 — актуальное техническое состояние

Этот документ — **единый технический ориентир для сопровождения и развития** текущего кода. Команды для пользователя находятся в [README](../README.md). Устаревшие отчёты итераций удалены из рабочей ветки, но остаются в Git history. Здесь разделены *подтверждённое регрессионными проверками*, *наблюдаемые диагностические свидетельства* и *нерешённые гипотезы*. Информация относится к состоянию проекта после консолидации 22.10.2026; дальнейшие изменения требуют повторного измерения.

## 1. Что делает проект и чего он не гарантирует

- Поддерживает ограниченный набор сериализованных Zend Encoder / PHP 5.2-файлов; это **не** произвольный PHP-байткод и не универсальный декодер ionCube/Zend.
- Возвращает `candidate_generated`, `unsupported` либо `not_encoded`. При непроверенном потоке управления/операндах должен **отказывать** (`fail closed`), а не выводить частичный PHP как законченный.
- Кандидат PHP, его синтаксическая валидность и совпадение с golden **не равнозначны** поведенческой эквивалентности исходной программы. Никакого подтверждённого source → encoded Zend stream → decompiled source round-trip пока нет.
- `--isolate-parser` ограничивает первичный разбор на Linux, но не является общей песочницей.

## 2. Актуальная архитектура и структура исходников

Рабочий код упакован как стандартный Python-пакет `src/zend_decompiler/`; **в корне нет исполняемых Python-модулей**. Импорты внутри пакета относительные, для запуска из исходников достаточно зависимости из `requirements.txt` и переменной `PYTHONPATH=src`. `pyproject.toml` определяет entry-point `zend-decompiler = "zend_decompiler.cli:main"`; альтернативный запуск — `python -m zend_decompiler`.

```text
src/zend_decompiler/
  __init__.py, __main__.py   публичный Python API и модульный запуск
  cli.py ────────────────> engine.restore_result() [единая точка восстановления]
   │                         ├── serial_parser.py (+ parser_isolated.py)
   ├── batch.py              ├── calibrate.py (+ evidence из data/opcodes/)
   │                         └── restore_core.py
   │                              ├── prefix_restore.py [выражения/TMP/VAR]
   │                              ├── cfg.py [CFG], crossblock.py [связи]
   │                              └── structure.py, state.py [эмиссия]
   ├── encoder_calls.py      семантика вызовов Encoder (отдельный слой)
   ├── encoder_foreach.py    структурное распознавание fetch/binding цикла
   ├── opcode_position.py    правило позиции opcode Encoder (отдельный слой)
   └── readonly_dataflow.py, triage.py, ir_evidence.py [read-only]
  assets.py                  пути к словарю, карте, тестовым эталонам
  block_previews.py, research.py, fuzz.py, alignment_audit.py,
  header_audit.py, compiler_oracle.py, partial.py [исследования]
data/opcodes/, data/research/ данные отдельно от Python-кода
tests/, golden/reference/     неизменённые регрессионные объекты
sample_inputs/, corpus/       испытательные входы и собственные фикстуры
```

Публичный API: `zend_decompiler.restore_result()`, `zend_decompiler.RestoreResult`; реализация в `zend_decompiler.engine`. Исследовательские CLI запускаются как `python -m zend_decompiler.<имя_модуля>` (например, `zend_decompiler.triage`), а не исполнением внутренних файлов по абсолютному пути. Изолированный парсер также использует `-m zend_decompiler.parser_isolated`.

Тесты импортируют только `zend_decompiler.*`. Работа ведётся с актуальным исходным деревом: для проверки используются локальные `unittest` и обработка `sample_inputs/`. Обратная совместимость с прежними API и CLI-обёртками не требуется.

## 4. Уровни достоверности opcode

- Активная карта: `data/opcodes/opcode_map.json` (377 ключей), метаданные `data/opcodes/opcode_map.json.meta.json`, provenance: `data/opcodes/opcode_evidence.json` (**368 записей `confirmed`**, 9 `unknown`, 1 `inferred`), гипотезы: `data/opcodes/opcode_map.json.meta.json (поле `hypotheses`)`, словарь: `zend_verified_dictionary.bin`.
- По сохранённому аудиту: **377** эмпирических ключей, из них **368 confirmed / 1 inferred / 9 unknown** evidence-записей (до подтверждения по второму корпусу было 313 ключей и 0 confirmed). Имя native opcode в таблице не означает, что сопоставление с ключом Encoder подтверждено независимой трассой.
- Не смешивать **native opcode ID** и **сырой ключ сериализации** вроде `1:199` (`позиция:значение`). Отсутствие native opcode 199 не объясняет ключ `1:199`.
- Сверка с официальным тегом [`php-5.2.17`](https://github.com/php/php-src/tree/php-5.2.17/Zend) подтверждает **побайтовое совпадение** сохранённых `zend_vm_opcodes.h` и `zend_compile.h`. Сохранённый `zend_vm_def.h` побайтово совпадает с веткой `PHP-5.2`, но **отличается от тега `php-5.2.17`** внутри `ZEND_SEND_REF (67)`; обработчики `ZEND_DO_FCALL (60)` и `ZEND_DECLARE_INHERITED_CLASS (140)` на исследованном участке согласованы с тегом. В `reference_headers_incompatible/` исторически находились заголовки более нового Zend Engine; они непригодны как эталон PHP 5.2. Эти отличия относятся к **native VM**, а не доказывают Encoder mapping.
- В кандидате заголовков семейства PHP 5.2: native `49 = ZEND_SWITCH_FREE`, `140 = ZEND_DECLARE_INHERITED_CLASS`; номер 199 там не определён. **Это не позволяет** назначать смысл сериализованному ключу `1:199` либо эмпирическому ключу, отнесённому таблицей к числу 140.
- `data/research/alignment.json` содержит архивное выравнивание и подозрения по `3:139`, `6:236`; исходные исторические трассы отсутствуют, поэтому эти выводы нельзя считать независимо подтверждёнными. Переприсвоение opcode без новых проверяемых свидетельств запрещено.

### Прямой вызов `SEND_* → DO_FCALL`: подтверждённый формат, ограниченная поддержка

В `src/zend_decompiler/call_protocol.py` и `prefix_restore.py` добавлена проверка прямой передачи аргументов без `INIT_FCALL_BY_NAME`. На собственном native compile-only примере `corpus/compile_only_dumps/01_calls.log` наблюдаются `SEND_VAL (65)` и `DO_FCALL (60)` с именем в `op1` и числом аргументов в `extended_value`.

Декодер допускает только упорядоченные аргументы с `UNUSED`-маркером сериализованного формата (`op2.word1 = 1`), строковое имя вызываемой функции, согласованный счётчик аргументов и полное завершение последовательности в текущем базовом блоке. Неподтверждённый opcode `140` не трактуется как `DO_FCALL` автоматически. При недостатке свидетельств генерация прекращается.

В `tests/test_call_protocol.py` и `tests/test_direct_calls.py` добавлены 19 позитивных и негативных тестов протокола; ещё 3 теста операции `DIV` находятся в `tests/test_native_division.py`. Всего проверены 104 метода, 101 прошёл, 3 пропущены. **Этот этап улучшил тестовую метрику и покрытие отдельных групп, но не файловую**; рост числа полных кандидатов с 8 до 9 получен позднее, на этапе вызовов Encoder по таблице символов файла.

Нативная операция `4 = ZEND_DIV` названа по `reference_headers_php52_candidate/zend_vm_opcodes.h` и поддержана в арифметическом декодере; эмпирическая карта не менялась. После этого `user_discount` стал генерируемым фрагментом, и `fun_all.php` имел **13 из 23** экспериментально обрабатываемых групп. После поддержки вызовов Encoder по таблице символов файла их стало **19 из 23**: не восстановлены `out_link` (TMP-слияние), `out_price` и `uc_rus` (неизвестный ключ `1:199` и несмоделированный `foreach`), `out_field` (`Complex FETCH_W`). **Полный файл не восстановлен.**

### Экспериментальные вызовы через `header_symbols` — только read-only

Модуль `src/zend_decompiler/header_call_hypothesis.py` проверяет **строго наблюдаемую гипотезу**, что ключи Encoder, эмпирически сопоставленные с native `140`, могут указывать на завершение вызова локальной функции, индексированной через `header_symbols`. Анализ требует evidence `unknown`, точной формы `UNUSED`/`VAR`, единственного локального определения, точных начальных `RECV` и упорядоченных `SEND_VAL`/`SEND_VAR` с целевым `extended_value = 60`. Он отвергает разорванные basic blocks, незавершённые вызовы и неподдерживаемые структуры; полная корректность CFG **не доказана** — проверка границ предполагает, что спорные инструкции не ветвятся.

На двух неподдерживаемых исходных файлах: **18** наблюдений, **15** `experimental_structural_match`, **3** `unverifiable_cfg` (все в `fun_all.out_price`; среди препятствий `FE_RESET/FE_FETCH` и отсутствие полного подтверждения ключей). Это **не** 15 подтверждённых native вызовов и **не** 15 восстановленных PHP-фрагментов. Ни декодер, ни `opcode_map.json`, ни уровни доказанности opcode не менялись. Дополнительные 23 Python-теста проверяют действительные позиции и негативные варианты путём копирования уже разобранных данных без добавления PHP-образцов. CLI анализатора выдаёт только JSON-диагностику; статус обоих файлов остаётся `unsupported`.

### Вызовы Encoder по таблице символов файла — отдельный слой, статус `inferred`

Гипотеза header-indexed calls из предыдущего раздела доведена до работающего правила декодирования, но **не на уровне native-операции**. Новая семантика описана отдельно от native-карты: `data/opcodes/encoder_call_map.json` (правила формы), `encoder_call_evidence.json` (наблюдения) и `encoder_call_map.json.meta.json` (SHA-256 и статус). Активные `opcode_map.json` и `opcode_evidence.json` **не изменены**; native-номер этих позиций остаётся нерешённым (140 в эмпирической карте, 200 в захвате поля `opcode` до назначения обработчика).

Форма терминатора вызова: `op1 = UNUSED(symbol_index, 1)` — индекс в `header_symbols` того же файла, `op2 = UNUSED(0, 1)`, `result = VAR`, `extended_value` — число аргументов; непосредственно перед ним идут `argc` инструкций `SEND_VAL`/`SEND_VAR` с `extended_value = 60` (native `DO_FCALL`) и маркерами позиций `op2 = UNUSED(1..argc, 1)`.

Правила fail-closed (`src/zend_decompiler/encoder_calls.py`): индекс в диапазоне `header_symbols` → символ объявлен **в этом же файле** → `argc` равен числу ведущих `RECV` вызываемой (неизвестная сигнатура, например `RECV_INIT`, отвергается) → `SEND_*` идут подряд, с корректными маркерами позиций и `extended_value = 60` → нет незакрытого предыдущего `SEND` → форма операндов терминатора и имя-идентификатор. Нарушение любого правила оставляет файл в `unsupported`; вызов не угадывается.

Кросс-проверка на текущем корпусе: **18 из 18** мест вызова разрешаются в функцию, объявленную в том же файле, и **18 из 18** совпадают `argc` и число `RECV` вызываемой (`currency_type`=3, `out_link`=1, `url_prefix`=0, `out_replace_teg`=1, `out_price`=5, `count_ln`=2, `send_mail`=2). Это **два независимых согласия**, а не независимое подтверждение: native-трассы того же защищённого потока не существует, статус остаётся `inferred`.

Результат: `links_fun(1).php` восстановлен целиком (6 из 6 групп, `structured_php`), в частности `send_mail($url_mail, $id_link)` и `count_ln($id_ln_groups, 0)`. Файловая метрика выросла **8 → 9**. `fun_all.php` остаётся `unsupported` по независимым причинам: двузначное TMP-слияние в `out_link`, несмоделированный `foreach` в `out_price`/`uc_rus`, `Complex FETCH_W` в `out_field`.

Проверки: `tests/test_encoder_calls.py` — 22 метода, включая 12 негативных случаев отказа (индекс вне диапазона, символ не объявлен, неизвестная сигнатура, `argc`≠`RECV`, посторонняя инструкция в цепочке `SEND`, незакрытый предыдущий `SEND`, маркер позиции, `extended_value`≠60, форма операнда `SEND`, неверный идентификатор, форма операндов терминатора, неизвестный байт, пустая таблица символов) и подделанный вход с исправленным индексом символа, который обязан остаться `unsupported`.


### Нативная форма `foreach` и `FETCH_W` — установлено собственным compile-only probe

Для закрытия оставшихся блокеров `fun_all.php` нативная форма цикла и ссылки проверена **собственным** compile-only probe на PHP 5.2.17 (образ `zend-php52-probe:local`, расширение `php52_probe.so`), с временными образцами **вне репозитория** и без исполнения кода.

Установлено:

* `global $x;` → `FETCH_W (83)` с `op1 = CONST` + `ASSIGN_REF (39)` с `op1 = CV`, `op2 = VAR`; оптимизатор 3.3.9 эту форму не меняет;
* `$a = &$b;` → одна `ASSIGN_REF (39)` с `op1 = CV`, `op2 = CV`;
* `foreach` **по значению** → `FE_RESET (77) extended = 0`, `FE_FETCH (78) extended = 1`, `OP_DATA (137)`, `ASSIGN (38)`, тело, `JMP (42)`, `SWITCH_FREE (49)`;
* `foreach` **по ссылке** → `FE_RESET (77) extended = 3`, `FE_FETCH (78) extended = 1`, `OP_DATA (137)`, `ASSIGN_REF (39)`, тело, `JMP (42)`, `SWITCH_FREE (49)`;
* `FETCH_W` над CV — это **переменная-переменная**: адрес переменной, названной значением CV. Форма `$$x = &$$y;` компилируется в `FETCH_W (83)` + `FETCH_W (83)` + `ASSIGN_REF (39)` с двумя VAR — ровно та форма, что стоит в `out_field`.

`OP_DATA = 137` объявлен в сохранённом заголовке `reference_headers_php52_candidate/zend_compile.h:575` (в `zend_vm_opcodes.h` этого номера нет, поэтому его легко пропустить). Это также уточняет прежнее наблюдение: значение **137**, снятое перехватом GDB, относится к *дополнительной* нативной инструкции рядом с `FE_FETCH` (она уже учтена в `calibrate.py` как `INSERTION`), а сериализованная инструкция на той же позиции — маркер ссылки, то есть `FETCH_DIM_TMP_VAR` (98), что и предсказывает правило позиции.

Правила декодирования, добавленные по этим данным:

* `FE_FETCH` в графе управления — двухстороннее ветвление (тело / выход цикла), `FE_RESET` — прямая инструкция; заголовок цикла с несколькими обратными рёбрами допускается, обход останавливается на заголовке;
* связывание переменной цикла распознаётся **по последовательности** `FE_RESET → FE_FETCH → связывание → присваивание`, а не по номеру опкода; восстанавливается `foreach ($arr as &$v) { … }`;
* элемент цикла не имеет выражения вне конструкции, поэтому его значение помечается маркером, а утечка маркера в оператор отвергает блок;
* машина состояний не умеет выразить `foreach` и **отказывает** для таких групп вместо искажённого кода;
* `FETCH_W` над CV рендерится как `$$name`, а `ASSIGN_REF` с двумя контейнерами — как `$a = &$b;`; форма `global $x;` распознаётся отдельно и сохраняется.

Итог: `fun_all.php` восстановлен целиком (23 из 23 групп), включая `out_price` и `uc_rus` с `foreach ($currency as &$row)` и `foreach ($ar as &$c)`, и `out_field` с `$$name_field = &$$name_field;` — последняя форма согласуется с тем, что в теле той же функции используется `${$name_field}`.

Остаётся `header_admin.php`: файл содержит несколько закодированных потоков, а декодер принимает ровно один; статус `not_encoded`, PHP не создаётся.

Проверки: `tests/test_foreach.py` — 10 методов (форма цикла, массив и переменная конструкции, маркер элемента не утекает, заголовок цикла, а также отказ при `FE_FETCH` без сброса, при связывании вне цикла, при чужом итераторе и при неподдерживаемой форме `FETCH_W`).

### Остальные формы операндов — по локальному корпусу

Эти правила добавлены после разбора остаточных отказов локального корпуса. Они действуют **на уровне декодера** и не меняют `opcode_map.json`, `opcode_evidence.json` или статусы подтверждённости ключей.

* **Структурный fetch `foreach`.** Оптимизатор в части файлов заменяет инструкцию fetch на общий обработчик, поэтому её native-номер не устанавливается. `encoder_foreach.py` распознаёт её по конструкции: инструкция без записи в карте идёт после `FE_RESET`, читает итератор этого сброса (TMP/VAR) и создаёт TMP. Связывание переменной цикла распознаётся по потоку данных от fetch и создаёт VAR. CFG, проверка неразрешённых индексов, `restore_core` и `state.py` используют один и тот же слой, поэтому неизвестный опкод не остаётся «незамеченным» в одном месте и «разрешённым» в другом.
* **Имена в cp1251.** Имена функций и переменных декодируются как cp1251, `sym()` принимает байты `0x80–0xFF` в идентификаторах. Это нужно для файлов сайта; синтаксис PHP 5.2 такие байты допускает, а проверка `php -l` подтверждает только синтаксис.
* **Массивы с ключами.** `zend_vm_def.h` PHP 5.2: `INIT_ARRAY`/`ADD_ARRAY_ELEMENT` берут значение из `op1`, смещение из `op2`; `UNUSED` означает добавление с очередным индексом. Поддерживаются только константные ключи (integer/string). `extended_value != 0` означает элемент по ссылке и **отвергается**, как и неконстантный ключ: иначе ссылка была бы потеряна.
* **`EXIT`.** Поддерживаются `UNUSED` (голый `exit;`) и константный статус (integer/string). Операнд TMP/VAR/CV **отвергается**: в контрольном и локальном корпусе таких форм нет, а native-свидетельства, что временный операнд здесь является статусом, тоже нет. Превращать его в голый `exit;` нельзя — это изменило бы поведение.
* **`UNSET_VAR`.** Строковый операнд — имя переменной, восстанавливается `unset($name);`; иные формы отвергаются.
* **`FETCH_FUNC_ARG`.** Обработчик PHP 5.2 читает значение `op1` как имя переменной. Поэтому константа даёт `$name`, а CV — `${$name}`, а не `$name`: эмиссия последней формы изменила бы программу. Остальные операнды отвергаются.
* **Обёртки `BOOL`/`BOOL_NOT`.** Доказательство короткого условия записывает точное отображение (`rendered_term`) и значения всех слотов обёрток. В итоговом условии чётное число отрицаний снимается, нечётное сохраняется; `BOOL` в условии не меняет истинность. Блок с join принимает либо композитное условие, либо собственное точное отображение; условие с потерянным отрицанием отвергается.
* **Терминальный `exit`.** Блок, заканчивающийся `exit;`, считается завершённым; `exit(<status>);` пока не считается доказанным завершением.
* **Ветвление `JMPZ_EX`/`JMPNZ_EX`.** Машина состояний принимает их наравне с `JMPZ`/`JMPNZ`: условие и полярность те же, различие только в записи результата сравнения.

Результат: локальный корпус **160 → 172 из 179** (7 отказов: 5 — неразрешённые TMP/структура, 2 — ошибки парсера), все 172 кандидата проходят `php -l` на PHP 5.2.17. Контрольный batch остался **10 из 11**, golden не изменились. Синтаксическая проверка не доказывает поведенческую эквивалентность.

Проверки: `tests/test_encoder_operand_forms.py` — 23 теста (массивы, `EXIT`, `UNSET_VAR`, `FETCH_FUNC_ARG`, cp1251-идентификаторы, негативные формы); `tests/test_short_circuit_wrappers.py` — 6 тестов (отрицание, чётность, точное отображение, чужой слот, потерянное отрицание); `tests/test_terminal_exit.py` — 3 теста; `tests/test_foreach.py` — 6 новых тестов структурного fetch и отказов.

### Правило позиции opcode — признано противоречивым и отключено от декодирования

Правило `native_opcode = base[байт] − (index mod 8)` выведено из эмпирической карты и воспроизводит все её ключи, но на втором корпусе предсказало неверно в **6 из 58** случаев; проверка формы операндов по заголовку PHP 5.2 поймала 11 из 16 ошибок, **5 ошибок прошли**. После расширения карты подтверждёнными ключами правило противоречит ей напрямую (четыре ключа: `4:26`, `5:7`, `6:230`, `7:160`).

Поэтому правило **больше не используется для декодирования**: ключ, которого нет в карте, остаётся неразрешённым. Правило сохранено как исследовательская запись со статусом `contradicted` (`data/opcodes/encoder_opcode_base.json` и его evidence). Связывание элемента цикла (ключ `1:199`) декодер узнаёт **по потоку данных**, а не по номеру опкода: нативный аналог этой инструкции оптимизатор подменяет на NOP, поэтому её собственного номера нет.

### Независимая статическая сверка с Zend VM PHP 5.2.17

Проверены *официальные* обработчики в [`zend_vm_def.h` выпуска `php-5.2.17`](https://github.com/php/php-src/blob/php-5.2.17/Zend/zend_vm_def.h) и сохранённая **compile-only native** трасса `corpus/compile_only_dumps/01_calls.log` для собственного PHP-исходника. Нативный `DO_FCALL (60)` определён как `ZEND_VM_HANDLER(60, ZEND_DO_FCALL, CONST, ANY)`: имя берётся из `op1` типа `CONST` и используется в поиске функции. Во всех 18 спорных записях сериализованного потока `op1.type == UNUSED (8)`, а `op1.word0` служит индексом `header_symbols`. Следовательно, прямое исполнение этих данных как **неизменённой native** инструкции `60` не соответствует ABI PHP 5.2; для вызова требовалось бы **дополнительное недоказанное преобразование** со стороны Encoder/Optimizer.

Нативный `DECLARE_INHERITED_CLASS (140)` вызывает `do_bind_inherited_class` и использует `extended_value` как ссылку на временный слот `class_entry`, а не как число аргументов вызова. Это подтверждает различие семантик штатных обработчиков, но **не устанавливает реальный смысл сырого ключа Encoder**. Собственный compile-only пример показывает `SEND_VAL (65, extended=60) → DO_FCALL (60, op1=CONST, argc=1)`, однако для защищённых входов **нет** независимой native-трассы **того же исполняемого потока** и нет подтверждённой пары source → Zend Encoder → Zend VM. Результат этапа: гипотеза header-indexed calls структурно согласована, но **не подтверждена независимо**, поэтому не интегрируется в эмиттер и evidence остаётся `unknown`.

### Перехват до назначения обработчика

В локальном Docker-образе с GDB перехвачен вход в экспортированную `zend_vm_set_opcode_handler()` при `php -l` с Zend Optimizer 3.3.9. Адрес каждой инструкции сопоставлен с индексом через исследовательский [`op_base_probe.c`](../research/diagnostics/op_base_probe.c); сценарии отладчика сохранены в [`trace_opcode.gdb`](../research/diagnostics/trace_opcode.gdb) и [`trace_user_handlers.gdb`](../research/diagnostics/trace_user_handlers.gdb). Смещения в сценарии относятся только к использованной x86_64-сборке PHP 5.2.17. Все **2107** вызовов (`1656 + 451`) удалось адресно связать с `op_array`; у всех 388 инструкций, сохранивших ненулевой `opcode` в поздней трассе, значение совпало с перехватом. Полные временные логи хранятся в `/tmp/zend-handler-map/` и не входят в проект.

На двух позициях сырого ключа `1:199` (`fun_all.out_price` #65 и `fun_all.uc_rus` #17) в поле `opcode` **до назначения обработчика** наблюдается **137**. В штатном `zend_vm_opcodes.h` PHP 5.2.17 номер 137 не определён; во всём compile-only прогоне `fun_all.php` для него не наблюдалась регистрация пользовательского обработчика. Это устанавливает значение поля в данной точке, **но не семантику** ключа; оба соседних участка содержат вставленный `NOP`, поэтому нельзя выпускать по ним готовый PHP.

Все 18 позиций, где эмпирическая карта предполагает `140`, имеют в этой точке значение **200**. GDB наблюдал регистрацию Zend Optimizer пользовательских обработчиков для `200`, `205`, `206` и `140`; общий адрес VM-обработчика не различал эти значения в предыдущем исследовании. Номер 200 отсутствует среди штатных opcode PHP 5.2.17. Остальные расхождения с картой сохраняются: два `70 → 0` рядом с `1:199` и два `66 → 65` с `CONST`-операндом. Из **2076** позиционно выровненных сериализованных записей 2052 совпадают с текущей эмпирической картой по числу, 22 расходятся, 2 ключа `1:199` не имеют назначения. Перехват происходит **после** внутреннего преобразования Zend Optimizer и до назначения VM-обработчика; исходный смысл расширенных `137`/`200` этим этапом не установлен. Результат остаётся `experimental` и не меняет карту, evidence, статусы файлов или основные метрики.

### Вызов как операнд короткого логического условия — контролируемое расширение

`crossblock.py` доказывал короткие логические условия только для чистых сравнений и одиночных чтений `FETCH_DIM_R`; вызов в операнде сравнения отвергался. Теперь вызов допускается: он декодируется как один замкнутый отрезок инструкций и встраивается в свёрнутое условие.

Свёртка меняет **момент выполнения вызова**, поэтому приняты три условия:

1. вызов обязан находиться в том же базовом блоке, что и короткое замыкание, — иначе его собственный оператор остался бы в блоке и вызов выполнился бы дважды;
2. ни один оператор этого блока не должен выводиться **после** вызова — иначе порядок вычислений изменился бы;
3. отрезок вызова обязан декодироваться целиком, иначе термин отвергается.

Для проверки пункта 2 декодер помнит, какая инструкция породила каждый выведенный оператор (`statement_sources`); проверку выполняет `structure.build_graph` до свёртки.

Результат на корпусе: `fun_all.php` → группа `out_link` восстанавливается целиком с условием `((strstr($REQUEST_URI, 'htm') == '') && ($old_search != 'y'))`; число обрабатываемых групп выросло **19 → 20 из 23**. Чистые доказательства (без вызовов) не изменились.

Проверки: `tests/test_crossblock_calls.py` — 9 методов (доказательство с вызовом, неизменность чистых доказательств, отказ при вызове без инициализатора, отказ при результате вызова не в том слоте, отказ при вызове вне блока замыкания, отказ при операторе после вызова, а также точная диагностика отказа на подделанном входе).

Диагностика отказа при этом усилена: аудит теперь называет точные инструкции несмоделированного управления (`unmodeled_control_flow`), точные недекодируемые индексы (`unknown_opcodes`) и находит блок по индексу даже без маркера блока в сообщении.

### Составное короткое условие — ограниченная свёртка

Для формы `(A || B) && C && (D || E)` `crossblock.py` объединяет два доказанных OR и один средний терм в одно доказательство. Принимаются только сравнения CV с константами и обёртки `BOOL`, без вызовов, чтений элементов массива или присваиваний на сворачиваемом участке. Проверяются слоты, цели переходов, непрерывное покрытие инструкций и входы промежуточных блоков; `structure.py` дополнительно требует, чтобы сворачиваемые блоки не выводили операторов. Порядок вычисления термов сохранён. Иные формы остаются `unsupported`.

На защищённом локальном корпусе это сняло один отказ: **172 → 173 из 179** полных кандидатов, осталось 6 отказов. Все ключи свёрнутого участка имеют статус `confirmed`, но поведенческая эквивалентность кандидата исходному PHP не доказана. Новый кандидат впоследствии отдельно прошёл `php -n -l` в локальном контейнере PHP 5.2.17; это подтверждает только синтаксис. `tests/test_nested_short_circuit.py` проверяет свёртку и отказы при нарушении целей переходов, слотов и входа блока на синтетическом Python op_array; это не подтверждение формата Encoder.

### Два вложенных чтения в коротком условии — ограниченная свёртка

Для подтверждённой девятиинструкционной формы `FETCH_DIM_R → FETCH_DIM_R → IS_NOT_EQUAL → JMPZ_EX → FETCH_DIM_R → FETCH_DIM_R → IS_NOT_EQUAL → BOOL → JMPZ` `crossblock.py` допускает два чтения с CV-основанием и CV-ключом в каждом терме. Обе цепочки должны читать одни и те же CV, сравниваться с разными строковыми константами и иметь точные producer/consumer-связи. Все девять ключей требуют статуса `confirmed`; проверяются CFG-рёбра, отсутствие посторонних входов и внешних потребителей временных значений. `structure.py` требует, чтобы первый блок начинался с первого чтения и не выводил операторов. Выражение сохраняет оба чтения и их порядок при коротком замыкании; прочие формы остаются `unsupported`.

Локальный результат: **173 → 174 из 179** полных кандидатов, контрольный набор **10 из 11**. Единственный новый кандидат прошёл `php -n -l` в контейнере PHP 5.2.17 без сети с файлом только для чтения. Сверка по SHA-256 всех входов показала единственный переход `unsupported → candidate_generated`; все прежние 173 кандидата побайтово совпали с базой. `tests/test_nested_dimension_join.py` содержит шесть положительных и отрицательных проверок на синтетическом Python op_array; они не подтверждают формат Encoder или поведенческую эквивалентность кандидата.

### Три вызова в коротком условии — ограниченная свёртка

Для формы `!call₁ && !call₂ && call₃` с двумя ранними `JMPZ_EX` правило проверяет замкнутые интервалы вызовов, совпадение слотов, три пути к общему `JMPZ`, отсутствие других входов и внешних потребителей TMP. Все opcode сворачиваемого участка должны быть `confirmed`. Первый блок может выводить операторы только до первого вызова; следующие блоки не должны выводить операторов. Это сохраняет порядок и условность выполнения всех трёх вызовов. Иные формы остаются `unsupported`.

На защищённом локальном корпусе это сняло один отказ: **174 → 175 из 179** полных кандидатов. Единственный новый кандидат прошёл `php -n -l` в контейнере PHP 5.2.17 без сети с файлом только для чтения. Все прежние 174 кандидата побайтово совпали с базой; контрольный batch остался **10 из 11**. `tests/test_three_call_short_circuit.py` содержит пять положительных и отрицательных проверок на синтетическом Python op_array. Синтаксическая проверка и native-семантика обработчиков не доказывают поведенческую эквивалентность исходному защищённому файлу.

### Присваивание вызова в условии цикла — ограниченная свёртка

Для подтверждённой формы `INIT_FCALL_BY_NAME → FETCH_FUNC_ARG → SEND_VAR → DO_FCALL_BY_NAME → ASSIGN → JMPZ_EX → IS_NOT_EQUAL → BOOL → JMPZ` правило проверяет точные слоты, цели переходов, непрерывную область CFG с обратным ребром к вызову, отсутствие посторонних входов и внешних потребителей TMP. `ASSIGN` переносится из оператора заголовка в первый терм `&&` только когда декодер вывел ровно этот оператор; иначе свёртка отклоняется. При каждой итерации вызов и присваивание происходят один раз, сравнение выполняется только при истинном первом терме. Иные формы остаются `unsupported`.

На защищённом локальном корпусе результат **175 → 176 из 179** полных кандидатов; остаются один отказ TMP/CFG и два отказа парсера. Единственный новый кандидат прошёл `php -n -l` в контейнере PHP 5.2.17 без сети с файлом только для чтения. Сверка по SHA-256 входов показала один переход `unsupported → candidate_generated`; все прежние 175 кандидатов побайтово совпали с базой. Контрольный batch остался **10 из 11**. Семь тестов `tests/test_assigned_loop_join.py` проверяют алгоритм на синтетическом Python op_array, включая отказы при нарушении слотов, переходов, входов CFG, повторного ребра, потребителей TMP и точного переноса присваивания. Это не доказательство формата Encoder или поведенческой эквивалентности кандидата.

### Правило позиции opcode Encoder — эмпирическая модель, статус `inferred`

Сериализованный поток хранит опкод инструкции в байте, значение которого зависит от позиции: `native_opcode = base[encoded_byte] − (instruction_index mod 8)`. Таблица `base` (**107** байтов) выведена из эмпирической карты и воспроизводит **313 из 313** её ключей без единого противоречия.

Правило оформлено отдельным слоем (`data/opcodes/encoder_opcode_base.json`, `encoder_opcode_evidence.json`, `encoder_opcode_base.json.meta.json` со своими SHA-256) и по правилам проекта:

* используется **только** там, где у эмпирической карты нет записи, и **никогда** не перекрывает запись карты;
* при загрузке сверяется с эмпирической картой и **отказывается работать** при любом расхождении;
* предсказание принимается, только если форма операндов совместима с обработчиком PHP 5.2 предсказанного опкода по сигнатурам из `reference_headers_php52_candidate/zend_vm_def.h` — это независимый источник, не архивная трасса; несовместимое предсказание отвергается;
* отрицательное предсказание и неизвестный байт отвергаются.

Следствие для `1:199`: `base(199) = 99`, позиция 1 → **98 = `ZEND_FETCH_DIM_TMP_VAR`**. Наблюдаемая форма (`op1` = TMP, `op2` = CONST, `result` = VAR) совместима с сигнатурой обработчика (`CONST|TMP`, `CONST`), а контекст — позиция сразу после `FE_RESET`/`FE_FETCH` внутри `foreach`. **Это модель, а не новое native-наблюдение**: native-доказательства для этой записи нет, evidence по-прежнему помечает ключ как `unknown`, а `opcode_map.json` и `opcode_evidence.json` не изменены.

Независимая сверка: **292** однозначных ключа архива `data/research/alignment.json` совпадают с правилом, противоречий нет; в двух ключах с несколькими кандидатами (`3:139`, `6:236`) предсказание входит в список кандидатов; ключ `1:199` в архиве кандидатов не имеет вовсе, поэтому правило его не опровергает, но и не подтверждает архивом.

Проверки: `tests/test_opcode_position.py` — 13 методов (воспроизведение всей карты, сверка с архивом, запрет перекрытия записей карты, отказ при противоречии, отказ по форме операндов, отказ для неизвестного байта, отказ для отрицательного предсказания, отчёт аудита).

В оставшемся TMP-случае `JMPZ` читает результат либо первого сравнения после вызова Encoder, либо второго сравнения. ## 6. Подтверждённые инженерные решения

- CFG: `EXIT = 79` является терминальным native opcode (обычное продолжение отсутствует); неподтверждённые рёбра для `BRK/CONT/FE_RESET/FE_FETCH/CATCH/THROW` должны приводить к консервативному отказу, а не к фиктивному fallthrough. **Native** семантика не подтверждает автоматически **Encoder** mapping.
- Синтаксический reaching-definitions обрабатывает back-edges и вход `undefined` отдельно. Для чтения с несколькими возможными определениями сохраняет неоднозначность; не удаляет `undefined` и не генерирует фиктивный литерал.
- Синтетическая ограниченная независимая проверка: **300/300** коротких CFG совпали между fixed-point и BFS-эталоном. Это свидетельство против локальных багов, но не всеобщее доказательство.
- `src/zend_decompiler/compiler_oracle.py` читает **compile-only native op_array** для *собственных* фикстур из `corpus/`. Адаптера native `op_array` → формат `SSG Team` и настоящего подтверждённого round-trip **нет**.
- Read-only инструменты должны сохранять контекст ошибки (operand-type, instruction index, путь, лимиты бюджета), не писать строковые литералы PHP/секреты и не воздействовать на PHP-эмиттер.

## 7. Приоритеты дальнейшего развития

1. **Доказательство соответствий:** получить проверяемое свидетельство именно преобразования Zend Encoder/Optimizer для того же самого вызова: сопоставимую native-трассу выполнения или достоверную собственную пару PHP 5.2 source → encoded serialized stream → native op_array **той же версии**, без расширения контрольного PHP-корпуса. Происхождение opcode-заголовка PHP 5.2.17 уже установлено, но это не доказывает правила сериализации. До такого свидетельства не назначать native семантику сырым ключам `140`/`1:199`, `3:139`, `6:236` или `FE_FETCH`. Для вызовов Encoder по `header_symbols` статус остаётся `inferred` именно по этой причине. Правило позиции opcode даёт для `1:199` **предсказание** `98`, но это модель, а не наблюдение: evidence по этому ключу остаётся `unknown`, и фиксировать его как native-соответствие без независимой трассы нельзя.
2. **Остаточные TMP и структура:** один файл локального корпуса блокируется слиянием двух определений TMP. Закрывать случай только при независимом подтверждении семантики вызова Encoder, уникальности producer и сохранения порядка и числа побочных эффектов; иначе `unsupported`. Операнд-результат нативного вызова в `crossblock` уже поддержан, `out_link` и `out_field` в контрольном наборе восстановлены.
3. **`foreach` — сделано (v29):** `FE_RESET`/`FE_FETCH` смоделированы в графе управления и в декодере, связывание переменной цикла распознаётся по последовательности инструкций, восстанавливается `foreach ($arr as &$v)`. Осталось независимое подтверждение: собственная native-трасса той же закодированной пары.
4. **Неподтверждённые формы операндов:** массив по ссылке (`extended_value != 0`), неконстантный ключ, `EXIT` с TMP/VAR/CV и динамическое имя аргумента вне форм из раздела 4 сейчас **отвергаются**. Расширять их только вместе с native-свидетельством той же пары, а не по аналогии.
5. **Постепенный типизированный IR:** добавить `Operand`/`SourceSpan`, ограниченный `Expr/Stmt` и последовательно расширять поддерживаемые конструкции PHP. Сохранение побайтового вывода прежних выпусков не обязательно.
6. **Тесты нового обработчика:** добавлять позитивные и отрицательные случаи, понятную диагностику отказа и проверять изменение числа полноценно обработанных файлов. Пересматривать эталоны вместе с обоснованными изменениями алгоритма, а не ради формального прохождения тестов.
7. **Воспроизводимость измерений:** локально запускать одинаковый набор тестов и обработку одних и тех же PHP-образцов. Отчитываться только о количестве успешных тестов и числе полностью обработанных файлов, не подменяя реальные результаты неподтверждёнными фрагментами.

Оба объединённых исследовательских файла содержат `schema_version`, `records`, `source_integrity`: исходные SHA-256 отдельных файлов и проверяемые SHA-256 нормализованных вложенных объектов. `tests/test_data_layout.py` сверяет структуру, привязки к активным данным и хеши объектов. Имена первоначальных JSON с `vNN` сохранены только в прежних Git-коммитах; поля версии, встречающиеся **внутри** неизменённых исторических свидетельств, означают происхождение данных, а не требование к версии движка.

Почему **не** слиты три активных opcode-файла: у карты, evidence и metadata различные проверяемые схемы; карта и evidence взаимно связаны SHA-256, а объединение изменило бы их байты и нарушило независимую golden-регрессию. Гипотезы, не являвшиеся самостоятельным исполняемым источником, безопасно включены в metadata.

Из корня удалены историческая карта `opcode_map_observed_v10.json`, серия снимков `validation_v19.json`–`validation_v28.json` (по существовавшим выпускам), а также `user_audit_v19.json` и `user_differential_v19.json`. Эти файлы не импортировались текущими скриптами/тестами и служили отчётами прошлых запусков. Их можно восстановить из Git history; действующие локальные тесты и проверяемые эталоны являются источником текущего статуса, а не старый `validation_vNN.json`.

JSON в `golden/reference/`, `corpus/`, `schemas/` и `tests/` сохранены. Старые пакетные отчёты и аудиты `examples/batch_v*` исключены из рабочей ветки; единственный исторический `batch_report.json` перенесён побайтово в `tests/fixtures/` для проверки схемы. Относительные ссылки внутри старого отчёта не являются действующими файловыми путями.

## 9. Критерии развития

1. Исходные PHP-образцы оставлять контрольным набором входов для сопоставимого подсчёта. Данные, opcode-карту и эталоны можно обновлять вместе с развитием алгоритма, но не для искусственного увеличения числа пройденных тестов.
2. При изменении формата `data/opcodes/` согласованно обновлять декодер, проверку SHA-256, тесты и документацию. Поддержка прежнего формата не обязательна.
3. Для новых исследовательских данных добавлять смысловые имена, проверяемое происхождение и актуальные тесты; не возвращать разрозненные старые отчёты в корень проекта.
4. Оценивать развитие только числом пройденных тестов и числом файлов со статусом `candidate_generated`. Архивные гипотезы не превращать в подтверждённые правила автоматически.

## 10. Правила размещения нового кода

1. Новые исполняемые Python-модули размещать только в `src/zend_decompiler/`; импортировать внутри пакета относительно (`from .assets import …`).
2. Для общих команд расширять `cli.py` и публичный `__main__.py`, не добавлять новые скрипты в корень.
3. Тесты хранить в `tests/`, данные — в `data/`, `corpus/`, `golden/`; внутренние форматы и текущие эталоны допускается обновлять без обязательства сохранять поведение прежних выпусков.
4. После изменений локально запускать `python -m unittest discover -s tests -v` и `python -m zend_decompiler batch sample_inputs -o /tmp/zend_batch --isolate-parser`; фиксировать два показателя: пройденные тесты и полностью обработанные файлы.
5. Изменение модульной структуры не является новым подтверждением семантики Zend Encoder: неизвестные opcode и отсутствие round-trip остаются ограничениями.
