# Zend Decompiler v28 — актуальное техническое состояние

Этот документ — **единый технический ориентир для сопровождения и развития** текущего кода. Команды для пользователя находятся в [README](../README.md). Устаревшие отчёты итераций удалены из рабочей ветки, но остаются в Git history. Здесь разделены *подтверждённое регрессионными проверками*, *наблюдаемые диагностические свидетельства* и *нерешённые гипотезы*. Информация относится к состоянию проекта после консолидации 22.10.2026; дальнейшие изменения требуют повторного измерения.

## 1. Что делает проект и чего он не гарантирует

- Поддерживает ограниченный набор сериализованных Zend Encoder / PHP 5.2-файлов; это **не** произвольный PHP-байткод и не универсальный декодер ionCube/Zend.
- Возвращает `candidate_generated`, `unsupported` либо `not_encoded`. При непроверенном потоке управления/операндах должен **отказывать** (`fail closed`), а не выводить частичный PHP как законченный.
- Кандидат PHP, его синтаксическая валидность и совпадение с golden **не равнозначны** поведенческой эквивалентности исходной программы. Никакого подтверждённого source → encoded Zend stream → decompiled source round-trip пока нет.
- Недоверенный/защищённый PHP и восстановленные кандидаты **не исполнять**. Допускается только статический разбор, а для синтаксиса — отдельно согласованный PHP `-n -l` без исполнения. `--isolate-parser` ограничивает первичный разбор на Linux, но не является общей песочницей.

## 2. Актуальная архитектура

```text
zend_cli.py ────────────────> zend_engine.restore_result()  [единая точка API]
   │                            │
   ├── zend_batch.py            ├── zend_serial_parser.py (+ isolated preflight)
   │                            ├── zend_calibrate.py (+ opcode evidence)
   │                            └── zend_restore_core.restore()
   │                                ├── zend_prefix_restore.py [выражения/TMP/VAR]
   │                                ├── zend_cfg.py [CFG]
   │                                ├── zend_crossblock.py [межблочные связи]
   │                                ├── zend_structure.py [структуры]
   │                                └── zend_state.py [консервативная эмиссия]
   └── dataflow/triage ─────> отдельные read-only анализаторы
```

- `zend_assets.py` централизует текущую карту opcode, словарь, схемы и golden-пути.
- `zend_readonly_dataflow.py`, `zend_triage.py`, `zend_ir_evidence.py`, `zend_block_previews.py`, `zend_alignment_audit.py`, `zend_header_audit.py`, `zend_compiler_oracle.py`, `zend_fuzz.py`, `zend_research.py` — специализированные диагностики/исследовательские утилиты. Их вывод **не** автоматически разрешает генерацию PHP.
- Публичный Python API: `zend_engine.RestoreResult` / `restore_result()`. Отдельных устаревших восстановителей и исполняемых `*_vNN.py` в корне нет.
- `pyproject.toml` описывает пакет `zend-decompiler-experimental`, версию `28.0.0`, Python >= 3.10 и `networkx>=2.8`. GitHub Actions проверяет Python 3.10/3.11/3.12.

## 3. Проверенная регрессия, а не обещание корректности

Последняя зафиксированная проверка после объединения реализаций:

| Контроль | Зафиксированный результат |
|---|---|
| `python -m unittest discover -s tests -q` | **72 теста: 69 успешно, 3 пропущены, 0 ошибок** |
| `python zend_cli.py validate` | Тот же набор |
| `python zend_cli.py batch sample_inputs -o … --isolate-parser` | **11 входов: 8 кандидатов / 2 unsupported / 1 not_encoded**, ожидаемый exit code 2 |
| 8 сгенерированных PHP-кандидатов | Совпадение с прежней кодогенерацией после исключения **только комментария версии** |
| Диагностические локальные блоки | **375 ранее успешных сохранены; 385 восстанавливаются текущим декодером** (плюс 10); это не подтверждает семантику PHP |
| Исходные образцы, dictionary, opcode-map, golden | Защищены SHA-256/тестами; не менять для маскировки регрессий |

`tests/fixtures/preview_completed_blocks.json` содержит отпечатки 375 ранее успешно восстановленных блоков; `tests/test_refactor_regression.py` проверяет сохранение каждого. `tests/test_golden.py`, `tests/test_single_core.py`, `golden/reference/manifest.json` закрепляют единое ядро и эталоны. Golden сравнивает **регрессию поведения программы-декомпилятора**, не фактическую правильность исходного Zend/PHP.

Три пропуска зависят от отсутствующих необязательных свидетельств/окружения (исторические probe-трассы, PHP 5.2 compile-only probe, отдельно предоставлявшиеся открытые исходники). **Не** считать их автоматически пройденными и не подменять фиктивными данными. Из-за отсутствия подтверждённой инфраструктуры PHP 5.2 и Encoder-oracle заявлять полный тест семантики нельзя.

## 4. Уровни достоверности opcode

- Активная карта: `opcode_map_observed_v20.json`, метаданные `opcode_map_observed_v20.json.meta.json`, provenance: `opcode_evidence_v21.json`, гипотезы: `opcode_hypotheses_v23.json`, словарь: `zend_verified_dictionary.bin`.
- По сохранённому аудиту: **313** эмпирических ключей, **305 inferred / 9 unknown / 0 confirmed** evidence-записей. Имя native opcode в таблице не означает, что сопоставление с ключом Encoder подтверждено независимой трассой.
- Не смешивать **native opcode ID** и **сырой ключ сериализации** вроде `1:199` (`позиция:значение`). Отсутствие native opcode 199 не объясняет ключ `1:199`.
- Сохранённые заголовки в `reference_headers_incompatible/` относятся к более современному Zend Engine и **не подходят** как источник PHP 5.2. Набор `reference_headers_php52_candidate/` согласуется с *семейством* PHP 5.2, но точное происхождение из PHP **5.2.17 не удостоверено**; дополнительно см. `header_verification_php52_candidate.json` / `header_verification_v24.json`.
- В кандидате заголовков семейства PHP 5.2: native `49 = ZEND_SWITCH_FREE`, `140 = ZEND_DECLARE_INHERITED_CLASS`; номер 199 там не определён. **Это не позволяет** назначать смысл сериализованному ключу `1:199` либо эмпирическому ключу, отнесённому таблицей к числу 140.
- `alignment_audit_v25.json` содержит архивное выравнивание и подозрения по `3:139`, `6:236`; исходные исторические трассы отсутствуют, поэтому эти выводы нельзя считать независимо подтверждёнными. Переприсвоение opcode без новых проверяемых свидетельств запрещено.

## 5. Конкретные нерешённые файлы

### `sample_inputs/fun_all.php` — unsupported

- Неизвестный ключ `1:199` наблюдается в `out_price` на инструкции **#65** и `uc_rus` на **#17**. Обе позиции имеют одинаковое локальное окно ключей `7:98, 0:24, 1:199, 2:42, 3:9` и совместимые типы операндов. Это корреляция, **не** определённая семантика. Read-only артефакт: `IR_EVIDENCE_V28.json`.
- В `out_link` чтение `TMP[2,0,0]` на **#16** имеет два синтаксически достижимых producer: **#13** (`JMPZ_EX`) и **#15** (`BOOL`). Путь, достижимый в CFG, не обязательно выполним при реальных значениях. Выбирать один producer и сворачивать в `&&` или `||` нельзя.
- Аналогичные предполагаемые CFG-слияния наблюдались в `currency_type` (#5/#8→#9), `out_field` (#28/#31→#32); автоматическая реконструкция условных выражений ещё **не доказана**.
- В сохранённом triage `TRIAGE_V27.json`: **23 группы**, из которых **15** поддаются синтаксическому read-only анализу; это не 15 семантически восстановленных PHP-функций. Новые диагностические блоки также не дают оснований выпускать полный кандидат.

### `sample_inputs/links_fun(1).php` — unsupported

- В `<main>` на **#12** есть `SEND_VAR` без надёжно восстановленного состояния открытого вызова.
- На **#14** сериализованный ключ `6:226` сопоставлен эмпирической картой со спорным native ID **140**; трактовка как `DECLARE_INHERITED_CLASS` **не подтверждена**.
- В сохранённом triage `TRIAGE_V27.json`: **6 групп**, **4** поддаются ограниченному синтаксическому анализу; без подтверждения контекста вызова/семантики opcode полный PHP запрещён.

## 6. Подтверждённые инженерные решения

- CFG: `EXIT = 79` является терминальным native opcode (обычное продолжение отсутствует); неподтверждённые рёбра для `BRK/CONT/FE_RESET/FE_FETCH/CATCH/THROW` должны приводить к консервативному отказу, а не к фиктивному fallthrough. **Native** семантика не подтверждает автоматически **Encoder** mapping.
- Синтаксический reaching-definitions обрабатывает back-edges и вход `undefined` отдельно. Для чтения с несколькими возможными определениями сохраняет неоднозначность; не удаляет `undefined` и не генерирует фиктивный литерал.
- Синтетическая ограниченная независимая проверка: **300/300** коротких CFG совпали между fixed-point и BFS-эталоном. Это свидетельство против локальных багов, но не всеобщее доказательство.
- `zend_compiler_oracle.py` читает **compile-only native op_array** для *собственных* фикстур из `corpus/`. Адаптера native `op_array` → формат `SSG Team` и настоящего подтверждённого round-trip **нет**.
- Read-only инструменты должны сохранять контекст ошибки (operand-type, instruction index, путь, лимиты бюджета), не писать строковые литералы PHP/секреты и не воздействовать на PHP-эмиттер.

## 7. Приоритеты дальнейшего развития

1. **Доказательство соответствий:** получить воспроизводимые пары только собственных PHP 5.2 исходников, их достоверных *encoded serialized* потоков и независимых native compile-only трасс **той же версии**. Подтвердить происхождение PHP 5.2.17 заголовков. Только после этого проверять `1:199`, ключи, связанные с 140, `3:139`, `6:236` и контексты `FE_FETCH`.
2. **Структура вызовов и TMP:** воспроизвести и покрыть отрицательными тестами `SEND_VAR`/call-state для `links_fun(1).php` и двузначные TMP-слияния `fun_all.php`. Устанавливать уникальность producer/side effects по доказательствам; иначе `unsupported`.
3. **Постепенный типизированный IR:** сначала независимые `Operand`/`SourceSpan` без изменения выхода; затем ограниченные `Expr/Stmt` и детерминированный рендеринг при сохранении golden; только после доказанного эквивалентного контракта переносить `foreach`, `list()`, `isset/empty`, `if/else`, `switch`, обработку исключений. Не переписывать всю эмиссию одним изменением.
4. **Проверка каждого нового обработчика:** позитивная и негативная фикстуры, явный fail-closed, SHA-256 эталонов, неподвижные старые успешные блоки, golden-код, режим пакетной проверки, отдельная проверка синтаксиса **без исполнения**. Новый эталон добавлять как новую версию данных только при обоснованном изменении поведения; старый не переписывать ради зелёных тестов.
5. **Эксплуатационная воспроизводимость:** поддерживать CI на Python 3.10–3.12, наличие `networkx`, wheel smoke-test, документировать внешние отсутствующие oracle/probe. Не включать реальные секреты или непроверенные исполняемые загрузчики в репозиторий.
