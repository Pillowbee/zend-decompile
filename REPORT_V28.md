# Zend Decompiler v28 — source-anchored CFG/IR evidence (read-only)

## Scope

Исходная база — архив v27. Входные защищённые `.php`, полученные от пользователя,
**не исполнялись**. При исследовании использован только разбор контейнера и
структур Zend IR. Восстановленные PHP-кандидаты также не исполнялись.

Сравнивались две открытые редакции `fun_all(1).php` и `fun_all_.php`, которые
пользователь предоставил отдельно. Они **не являются аттестованными исходниками**
закодированного `fun_all.php`; их тексты не копируются в распространяемый архив.

## 1. Базовая регрессия

До изменения кода: `python -m unittest discover -s tests -q` — **57 тестов,
0 ошибок, 2 пропуска**. Заложенный в v27 пакетный анализ дал 8 кандидатов,
2 `unsupported`, 1 `not_encoded`.

В v28 добавлен только модуль `zend_ir_evidence_v28.py`, 13 собственных
проверок (контроль формы, лексических ориентиров, реальных офлайн записей).
Ядро эмиссии PHP, словарь, таблица соответствий, evidence, golden не менялись.

## 2. Unknown-key `1:199`: повторяемость контекста, но НЕ native opcode

Анализ без PHP Loader выявил:

| Функция закодированного файла | Инструкция | Context fingerprint |
| --- | ---: | --- |
| `out_price` | #65 | `05c4ef26a9a85a5aaf91eb96347006304d2ae0588f1a336184efa547fd443144` |
| `uc_rus` | #17 | тот же |

В обеих точках одинаково окно пяти сырых ключей:
`7:98`, `0:24`, `1:199`, `2:42`, `3:9`, а также **типы** операндов.
По сохранённому *гипотетическому* mapping первые две позиции похожи на
`FE_RESET` и `FE_FETCH`, а после неопределённого `1:199` следуют
`ASSIGN` и `FREE`. **Эти нативные имена не доказаны независимым oracle.**

В двух открытых редакциях соответствующие функции содержат `foreach`.
Это положительная структурная корреляция, но **из одного и того же
вхождения нельзя вывести семантику неизвестного opcode**. Есть
дополнительная модельная проверка, что смена типа операнда меняет
fingerprint даже при сохранении числового ключа.

## 3. TMP merges на коротких ветвях

Новый консервативный распознаватель проверяет: условную ветвь
`JMPZ_EX`/`JMPNZ_EX`, запись в TMP, потенциальную запись в тот же TMP
из `BOOL` в другой ветви, чтение в месте слияния и независимые CFG
пути к обоим производителям. PHP `&&/||` он **не реконструирует**.

На фактическом бинарном потоке найдено:

| Функция | Условный producer | BOOL producer | Чтение TMP |
| --- | ---: | ---: | ---: |
| `out_link` | #13 | #15 | #16 |
| `currency_type` | #5 | #8 | #9 |
| `out_field` | #28 | #31 | #32 |

Для этих случаев сохранены оба BFS-свидетельства. Это объясняет
неоднозначности v27 на уровне **синтаксических определений**, а не
показывает выполнимость путей с реальными значениями. Неподтверждённые
source-версии и отсутствие Encoder-oracle не разрешают генерацию PHP
для этих групп.

## 4. Лексические открытые ориентиры

| Файл | Байтов | Лексических PHP функций | SHA-256 |
| --- | ---: | ---: | --- |
| `fun_all(1).php` | 42402 | 53 | `4e4b3dd7e75a867848d7dcf4ef4dd43ef06a3ab529afefbb090b4ccd7157e720` |
| `fun_all_.php` | 41294 | 51 | `2cd08e506eb6f4b740a66659ace13083d4436ef432483bcb814edd80a6943602` |

Модуль удаляет HTML/JS-фрагменты, строки и комментарии из используемой
лексической маски, затем проверяет наличие объявлений функций и `foreach`.
Это **не полный парсер PHP** (не анализируются heredoc и все особые лексемы),
поэтому все признаки помечены как подсказки, никогда не как доказательства.
В JSON не копируются исходники, строковые литералы, пароли или SQL.

## 5. Проверяемые результаты и границы

- **70 unit tests, 0 failures/errors, 2 skips** (`python -m unittest discover -s tests -q`).
- SHA-256: **16/16 golden outputs**, **11/11 inputs**, словарь и mapping
  согласно манифесту; bytes таблицы evidence, словаря и golden manifest
  идентичны v27.
- Пакетный режим `python zend_cli.py batch sample_inputs -o /tmp/v28_batch
  --isolate-parser`: exit **2 (ожидаемо)**; **8 candidate_generated,
  2 unsupported, 1 not_encoded**.
- Пакетные файлы v27 и v28 побайтово совпадают (в том числе отчёты).
  Выходных исполняемых PHP для `fun_all.php` и `links_fun(1).php` нет.
- Не выполнялись PHP-код, Zend Optimizer, компиляция защищённых файлов,
  PHP lint или попытки доказать семантическую эквивалентность.
- 18 контекстов неопределённых/оспариваемых key; 2 повторяющихся формы
  (включая `1:199`), 3 узких кандидата на CFG join.

## 6. Воспроизведение

```bash
python -m unittest discover -s tests -q
python zend_ir_evidence_v28.py sample_inputs/fun_all.php \
  '/path/to/fun_all(1).php' '/path/to/fun_all_.php' -o /tmp/ir_v28.json
python zend_cli.py batch sample_inputs -o /tmp/batch_v28 --isolate-parser
```

Для точной регенерации отчёта нужны два отдельных исходных PHP-файла
с приведёнными SHA-256 (в архив их не клонировали). Машинный артефакт:
`IR_EVIDENCE_V28.json`. Прогресс выражен в **структурной проверяемости**, а
не в увеличении числа расшифрованных файлов. Кодирование собственного PHP
с доказанной Encoder/native парой остаётся необходимым для назначения
opcode `1:199` и подтверждения гипотез об управлении.
