# AGENTS.md — правила работы AI-агентов

Действует на весь репозиторий. Здесь фиксируются **полномочия и порядок работы агента**, а не устройство декомпилятора или его текущие результаты.

Перед каждым этапом читать актуальные:
- [README.md](README.md) — назначение, запуск, тестирование и **две основные метрики** проекта.
- [docs/PROJECT_STATUS.md](docs/PROJECT_STATUS.md) — архитектура, доказательства, ограничения, нерешённые проблемы и текущие результаты.
- Соответствующие исходники и тесты в текущем `main`.

Не переносить в этот файл описание модулей, команды CLI, численные показатели, историю исследований и перечни opcode: эти сведения должны оставаться в указанных документах. При противоречии документов или неясности полномочий запросить решение владельца, не делать предположений.

## Обязательные решения владельца

1. **Если пользователь явно запросил коммит, выполнять его напрямую в `main`.** Не создавать ветки и Pull Request, если владелец явно не изменил это правило. Само согласование разработки не является разрешением на коммит.
2. **Согласовывать каждый этап.** До изменения кода или данных представить цель, границы работ и проверки; дождаться явного согласия. Одобрение этапа не распространяется автоматически на следующий этап или расширение задачи. Действия внутри одобренного этапа отдельного разрешения не требуют, **кроме коммита**.
3. **Допускать крупный рефакторинг без немедленного роста метрик**, если он обоснован и согласован. Не называть такой рефакторинг измеренным улучшением.
4. **Разрешать экспериментальные реализации только с явной пометкой `experimental` / «не подтверждено».** Они не должны автоматически влиять на подтверждённые соответствия opcode, полноценные результаты декомпиляции и основные метрики. Подробные критерии достоверности — в `PROJECT_STATUS.md`.
5. **Не расширять PHP-корпус.** Запрещено добавлять собственные PHP-фикстуры, новые закодированные образцы и поддельные сериализованные потоки: нет доказательств, что они воспроизводят оригинальный энкодер. Не менять контрольные `sample_inputs/`. Новые Python-тесты алгоритмов допустимы, но синтетические данные не подтверждают формат Zend Encoder.
6. **Повышать версию только после подтверждённого роста хотя бы одной из двух основных метрик без регрессии другой.** Пропуски, изменение эталонов ради прохождения тестов, число частичных функций и неподтверждённые результаты не считаются ростом.
7. **Всегда откатывать регрессии.** При потере любого ранее успешного теста или ранее полного результата `candidate_generated` вернуть `main` к рабочему состоянию, повторить проверки и сообщить причину. Нельзя скрывать регрессию ослаблением тестов или переписыванием golden без технического обоснования.
8. **Останавливаться после выполнения согласованной задачи.** Предоставить итог и не начинать новый этап без следующего согласования. При блокировке описать причину и также остановиться.
9. **Коммит в репозиторий делать только по явному запросу пользователя.** Не создавать коммиты автоматически после реализации, успешных тестов или завершения согласованного этапа. Запрос на разработку, проверку либо одобрение плана сам по себе не означает разрешения на коммит. До запроса на коммит сообщить о готовых изменениях и проверках; коммитить только после прямого указания пользователя.
10. **Использовать GitHub только для версионирования проекта.** Допустимы чтение исходников и истории изменений, а также коммиты по отдельному явному запросу пользователя. **Запрещено использовать GitHub Actions для запуска, перезапуска или выполнения тестов, сборок, анализа кода и измерения метрик.** Не запускать рабочие процессы через GitHub API или веб-интерфейс, не считать результаты GitHub Actions подтверждением выполненных агентом проверок. Все тесты, пакетные прогоны и иные проверки выполнять **локально в рабочем окружении агента**. Если локальное выполнение недоступно, честно сообщить, какие проверки не выполнены, и не заменять их GitHub Actions.

## Порядок выполнения согласованного этапа

1. Зафиксировать исходный commit SHA и проверить актуальное состояние нужных файлов. Ознакомиться с техническими ограничениями в `PROJECT_STATUS.md`.
2. Выполнить **только согласованную работу**, сохранив принципы безопасного декодирования, описанные в основных документах.
3. Добавить или уточнить содержательные положительные и отрицательные регрессионные тесты, где они необходимы. Не создавать новые PHP-образцы.
4. **Локально** выполнить предусмотренные в `README.md` полный набор тестов и пакетную обработку исходного корпуса. Проверить отсутствие потерь относительно исходного состояния. Если локальная среда недоступна, явно указать непроверенные результаты; **не использовать GitHub Actions как замену локальным проверкам**.
5. При регрессии откатить неподтверждённые изменения и проверить восстановление исходных показателей. Если регрессия уже попала в `main`, согласовать исправляющий коммит с пользователем. Без регрессии **не коммитить автоматически**: подготовить изменения и дождаться прямого запроса пользователя на коммит в `main`.
6. Обновить существующие `README.md` и/или `PROJECT_STATUS.md` **только если** изменилась информация, за которую они отвечают. Не создавать отдельные версионные отчёты.
7. Отчитаться о выполненных изменениях, **локальных** проверках, **двух основных метриках «до → после»** (только если они фактически измерены), пропусках и ограничениях проверки. Если пользователь отдельно запросил коммит и он создан, указать его SHA. Не ссылаться на GitHub Actions как на результат проведённого тестирования.
8. Завершить работу. Следующие действия требуют нового согласования.

## Границы ответственности документов

- В `AGENTS.md` менять только **правила поведения и полномочия агентов**.
- В `README.md` поддерживать пользовательские инструкции и способ измерения результатов.
- В `docs/PROJECT_STATUS.md` поддерживать технические решения, наблюдения, ограничения и текущий статус.

Если владелец меняет процесс работы, обновлять этот файл; если меняется реализация, не копировать её описание сюда.
