# AGENTS.md — инструкции для AI-агентов Zend Decompiler

Файл действует на весь репозиторий. Это **правила работы**, а не самостоятельный отчёт о состоянии проекта. Перед каждой задачей читайте актуальные `README.md`, `docs/PROJECT_STATUS.md` и соответствующие исходники ветки, с которой работаете. Репозиторий — основной источник истины; исторические сообщения, сохранённые фрагменты и старые результаты не заменяют текущее состояние кода.

## Назначение и критерии успеха

Zend Decompiler — экспериментальный офлайн-декомпилятор ограниченного формата сериализованных Zend Encoder / PHP 5.2-файлов. Восстановленный код — **кандидат**, а не доказанно эквивалентный оригинал.

Единственные метрики успеха разработки:

1. **Число успешно пройденных автоматических тестов.** Не включайте skipped, failed, errors или expected failures в passed. Не ослабляйте проверки и не добавляйте формальные/тривиальные тесты только ради числа.
2. **Число полностью обработанных закодированных файлов** из неизменённого контрольного набора `sample_inputs/`, получивших статус `candidate_generated`. Не учитывайте `unsupported`, `not_encoded`, отдельные функции, исследовательские фрагменты и неполный результат.

Не подменяйте эти показатели числом распознанных opcode, восстановленных групп, покрытых инструкций, строк PHP или успешных синтаксических проверок. Промежуточные показатели разрешены только для диагностики.

Числа в документации — последнее **зафиксированное** измерение, а не автоматически актуальное. После изменений измеряйте заново и явно указывайте, где и на каком commit SHA выполнялись проверки.

## Безопасность и достоверность

- Никогда не **исполняйте** защищённые входные PHP-файлы, восстановленные кандидаты или неизвестные Zend-загрузчики/расширения. Работайте статически. Для PHP, если это согласовано и доступно, допускается только отдельная синтаксическая проверка `php -n -l`, не доказывающая эквивалентность.
- `--isolate-parser` — ограниченная изоляция парсера на Linux, **не** полноценная песочница.
- Применяйте принцип **fail closed**: при неизвестном opcode, операнде, недоказанной семантике вызова или ветвления, неоднозначном TMP/VAR либо неполном покрытии инструкций возвращайте `unsupported`, а не фиктивный PHP.
- Не выдавайте частично восстановленный код за законченный `candidate_generated`. Не генерируйте работоспособно выглядящую замену файла с пропущенными функциями/инструкциями или заглушками вместо неизвестной логики.
- Различайте сырой сериализованный ключ (например, `1:199`) и **native opcode ID**. Не назначайте новые соответствия по совпадению номера или сходству соседних инструкций.
- Различайте `confirmed`, `inferred` и `unknown`. Не повышайте достоверность гипотез без независимых, воспроизводимых свидетельств; не переносите вывод из собственных compile-only трасс автоматически на чужой encoded-поток.
- Не запускать реальный PHP ради проверки предполагаемого поведения защищённого образца. Собственные PHP-фикстуры из `corpus/own_sources/` можно исследовать только предусмотренными compile-only методами.

## Архитектура и размещение

- Рабочий Python-код находится **только** в `src/zend_decompiler/`. Не создавайте новые исполняемые Python-скрипты в корне. Внутри пакета используйте относительные импорты.
- Общие команды расширяйте через `cli.py` / `__main__.py` и единый `engine.restore_result()`; не вводите параллельные движки восстановления.
- Тесты — `tests/`, образцы — `sample_inputs/`, текущие эталоны — `golden/reference/`, сведения о соответствии opcode — `data/opcodes/`, исследования — `data/research/` и `corpus/`.
- Сохраняйте последовательность вызовов, порядок вычислений, побочные эффекты и границы CFG. Для межблочных временных значений используйте доказуемые dataflow/CFG-связи; не выбирайте произвольный producer.
- **Обратная совместимость не требуется.** Допускается менять архитектуру, API, форматы и эталоны, если изменение технически обосновано, покрыто содержательными тестами и улучшает декомпилятор.
- Не создавайте дублирующиеся PHP-файлы, версионные копии результатов и отдельные отчёты `vNN`. Результаты экспериментов складывайте во временную директорию **вне** репозитория. Не изменяйте исходные защищённые образцы ради роста метрик.

## Ожидаемый рабочий цикл

1. Прочитайте актуальную документацию и код, зафиксируйте текущую ветку/commit SHA и причины отказа на целевых файлах.
2. Выберите конкретное техническое препятствие и определите, какие корректные конструкции новый код позволит обрабатывать.
3. Добавьте **положительные и отрицательные** регрессионные тесты: успешный разбор, отказ для неподтверждённых форматов, неоднозначности, нарушение протокола и побочные эффекты.
4. Реализуйте минимально достаточное, проверяемое исправление. Не маскируйте ошибки и не меняйте карту opcode без источников и контроля целостности.
5. Запустите полный набор тестов и batch на неизменённых `sample_inputs/`. Проверьте, что ранее генерировавшиеся полные кандидаты не регрессировали.
6. Укажите только две главные метрики «до → после», число пропусков отдельно, список всё ещё неподдерживаемых файлов и точные ограничения проверки. Не объявляйте CI-проверку «локальной».
7. Обновите существующие `README.md` и `docs/PROJECT_STATUS.md`, если изменились реализация, ограничения или подтверждённые результаты. Не создавайте отдельные отчёты для выпусков.

## Команды проверок

Из корня checkout (Python 3.10+, зависимость `networkx`):

```bash
python -m pip install -r requirements.txt
export PYTHONPATH=src
python -m unittest discover -s tests -v
python -m zend_decompiler batch sample_inputs -o /tmp/zend_batch --isolate-parser
```

Используйте новый пустой выходной каталог для каждого batch-прогона, не перезаписывайте существующие результаты. Возврат batch с кодом **2** при наличии `unsupported` допустим и сам по себе не означает регрессию. Числа извлекайте из полного вывода `unittest` и `batch_report.json`, а не из заголовков старых документов.

В `.github/workflows/metrics.yml` есть независимая проверка в чистом checkout. Если локальный запуск недоступен, можно опираться на GitHub Actions, но это нужно явно назвать и указать ссылку на завершившийся прогон. Нельзя утверждать, что тесты выполнялись локально, если выполнялся только CI.

## Обновление данных и golden

- Изменяйте `golden/reference/` только вместе с обоснованным изменением алгоритма; сравнение с текущим golden не является доказательством семантической эквивалентности.
- Для изменений `data/opcodes/` согласованно проверяйте карту, evidence, metadata, SHA-256, тесты и документацию; источник нового соответствия должен быть воспроизводим.
- Не вносите исторические диагностические артефакты в активный код и не считайте сохранённые исследовательские отчёты независимым oracle.
- Новые тесты должны доказывать новое поведение или предотвращать реальную регрессию, а не только увеличивать значение счётчика.

## Коммуникация и внесение изменений

- Пользуйтесь подключённым GitHub для чтения и изменения удалённого репозитория. Не утверждайте, что изменили файл или запустили проверку, пока результат не подтверждён.
- Следуйте явно указанной пользователем ветке и режиму доставки изменений; **постоянная политика direct push vs PR пока не согласована**.
- Сначала сообщайте, что изменено и какие проверки подтверждены; затем — обе метрики, оставшиеся препятствия и следующий обоснованный технический шаг.
- При недостатке данных для безопасного декодирования сохраняйте точную причину `unsupported`, не подменяйте её предположительным PHP.

Дополнительные организационные предпочтения (допуск прямых коммитов, процесс review, степень автономности и стратегия тестовых фикстур) должны быть уточнены у владельца проекта и затем внесены сюда без дублирования `PROJECT_STATUS.md`.
